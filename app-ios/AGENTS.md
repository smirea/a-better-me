# Stack

- Language: Swift
- Minimum target: the newest iOS (27), iPhone only, portrait, dark mode. No legacy support: use the newest APIs freely and never add `#available` fallbacks.
- Prefer native SwiftUI components and Liquid Glass over custom ones. Style native components with `DesignSystem/` tokens before building a replacement.
- Keep dependencies rare and intentional

# Development

- Run `./scripts/run` to build, install, and launch the app, with automatic rebuild and relaunch after saving. Requires Bun and Xcode. Stop with Ctrl-C, or use `--no-watch` for one launch.
- Use `./scripts/run --targets` to list devices and simulators; `*` marks the effective default. Select with `-t simulator` or `-t "iPhone 17"` (also accepts an identifier). It opens Device Hub on Xcode 27 or Simulator.app on earlier Xcode versions.
- Selection precedence is `-t` / `--target`, then `SWIFT_RUN_DEFAULT_TARGET`, then a connected iOS device, booted simulator, or available simulator. Duplicate simulator names prefer a booted instance, then the newest runtime; use an identifier to select exactly. Add simulator runtimes in Xcode's settings.
- Physical devices need Xcode pairing, Developer Mode, and an unlocked screen. Configure automatic signing in Xcode, pass `--team`, or set `SWIFT_RUN_DEVELOPMENT_TEAM`.
- Edit SwiftUI code and resources in `Sources/App` (iPhone), `Sources/Watch` (watch app), `Sources/Widgets` (Live Activity, widgets, and the control), and `Sources/Shared` (compiled into all three); Xcode picks up new files automatically. Building the `App` scheme builds and embeds the other two. Open `App.xcodeproj` and use the shared `App` scheme for debugging.
- Build errors leave the watcher running; fix the error and save again. Build output is in `DerivedData/device/build.log`, or `DerivedData/simulator/build.log`. Drive the running app with T3 Code's device tools: `device_open` on your own simulator returns the exact path of an `agent-device` command bound to that device and session, so it needs no flags. Run that path as is, never through a wrapper of your own (`snapshot -i`, `fill`, `screenshot`), and tap by label: `press 'label="Save"' --settle`. Give interactive elements accessibility labels so snapshots name them and presses find them.
- Agents run their worktree's own simulator headless: `./scripts/run -t "$(agent-simulator udid)" --headless --no-watch` builds, installs, and launches without opening Simulator.app or Device Hub. `agent-simulator udid` creates the simulator on first use, named after the worktree directory (the newest iPhone Pro on the newest iOS), and claims it; `agent-simulator udid 2` gives a second one. Drop `--no-watch` to rebuild on save. Drive the app with T3 Code's device tools, never raw `simctl`: `device_open` streams the simulator into the thread's Device panel (no window on the Mac).
- To test with a watch, add `--pair-watch`: `./scripts/run -t <udid> --headless --pair-watch` pairs your simulator with a watch (the newest model on the newest watchOS, reusing an existing pair), boots both while the app builds, installs and launches the watch app, and prints the watch's udid. Clean up with `./scripts/run -t <udid> --delete` (a udid only, never a name), which shuts down and deletes the simulator and its paired watches; `simctl delete` of the phone alone leaves the watch behind.
- Debug simulator builds have Apple Health off (`HealthStore.isAvailable`), so no Health sheet appears and Health features behave as if access were denied. To work on Health, run `./scripts/run --health on` once: the app saves the choice, so later launches from any tool keep it, the run seeds 60 days of weights, steps, flights climbed, and walking distance into Health (`HealthSeed`, each type only while Health has none of it), and it answers Health's sheet. `--health off` turns it off again. Release builds and device builds always use Health. `agent-device` can't read or press anything on Health's sheet ([callstack/agent-device#4226](https://github.com/callstack/agent-device/issues/4226)), so never answer it by hand: look at it with `device_screenshot`, then run `./scripts/run -t <udid> --headless --no-watch --grant-permissions`, which relaunches the app and answers the sheet's Select All, so a type a change just added (such as Flights Climbed) is granted too.
- Simulators start with every other permission granted. The app asks for all of them at every launch (`AppPermissions`) and, in Debug simulator builds, records in its defaults whether that launch got every prompt answered. When the last launch didn't (a fresh install, or a launch killed with a prompt up), `scripts/run` runs the `GrantPermissions` scheme's UI test (`UITests/App/PermissionsGrant`), which answers each system prompt, and Health's sheet when Health is on, until the app reports them all answered; that adds about 30 s once per simulator, and a failed grant fails the run. `--grant-permissions` answers them again, for example after a change adds a Health type. The test reads each element through `snapshot()` and taps the frame's coordinates, because a query that loses its element (Health's sheet swaps a progress indicator for a button while it loads) fails and ends a UI test on the spot, and Health's frames come relative to the sheet, so it adds the sheet's origin. Don't run `simctl privacy grant all`: it resets the app's Health access too. `scripts/run` also grants Motion to `com.apple.Health` (Fitness Tracking), without which a phone-recorded workout start opens Settings ([Live workout surfaces](../docs/decisions/live-workout.md#apple-health)). To test a denied state, revoke it in the Settings app (Privacy & Security, or Health > Data Access & Devices) or with `xcrun simctl privacy <udid> revoke <service> com.stefan.a-better-me`.
- T3's device tools don't list watch simulators. Drive the watch app with `./scripts/watch-drive <watch-udid|phone-udid> start` (a phone udid drives its paired watch), then `tap <label>`, `crown <delta>`, `swipe left|right|up|down`, `home` (the Digital Crown press: the watch face, then the Smart Stack with `crown 1`), `shot <path>`, `tree`, and `systap com.apple.Carousel <id>` for system sheets such as Health access; `stop` ends it. It runs a UI test, which boots the paired iPhone, so to test the watch without the phone shut the iPhone simulator down after `start`. On the watch's Health sheet, pick Full History before Done, which stays disabled until then. Workout mirroring never reaches the phone between simulators (Rapport has no paired companion there), so everything runs over WatchConnectivity; test the mirror on real devices.
- If every simulator launch or `xcodebuild test` hangs while the app process sits stopped (`ps` state `T`), a stale `debugserver` is waiting on a macOS developer-tools authorization prompt that may never be visible. Kill the stale `debugserver` processes and `SecurityAgent`, then relaunch.
- Every build, Debug and Release, opens the Feedback editor on shake (`Feedback.enable()` in `App.swift`). When you build or change a screen, row, card, or chart, follow Feedback's accessibility skill: built-in accessibility first, then `.feedback` tags until a single tap on any region selects it unambiguously. Read the latest with `gh api repos/smirea/feedback-engine/contents/skills/feedback-accessibility/SKILL.md -H 'Accept: application/vnd.github.raw'`. Trigger it on a simulator with `xcrun simctl notify_post <udid> com.apple.UIKit.SimulatorShake`.
- Clean up before reporting: `agent-device close` ends the session, then `device_close` with `shutdown: true` powers the simulator off. `device_close` only shuts down a device still open in the thread's panel, so keep it there until this step. A session left open locks the device, and the next agent gets `DEVICE_IN_USE`. `scripts/run` claims the simulator it targets for the worktree it runs from (`agent-simulator claim`), and removing a merged worktree (settle, `agent-t3-worktree gc`, or `agent-t3-worktree teardown`) deletes its simulators with their paired watches, so an agent in a worktree deletes nothing itself. `agent-simulator gc` shuts claimed simulators down after 15 idle minutes. A headless boot waits (`agent-simulator wait`) while the Mac's total CPU is above 70% or 4 iPhone simulators are booted, and exits 3 after 3 minutes: rerun it.
- Debug simulator builds seed themselves at launch (`Sources/App/DevSeed.swift`): each empty area gets realistic history, 30 workouts, an active program, 45 days of food, quick adds, and 36 weigh-ins, and a food library (custom foods, recipes, and favorites), so lists hold 20 to 50 rows. Run with `scripts/run --no-seed` (it passes `-noSeed` to the launch and the permission grant) for an empty store (a relaunch through `agent-device open --relaunch` needs `--launch-args -noSeed` again, or the seed runs), or for the owner's data restored into the worktree's server with `bun scripts/restore-backup.ts` after uninstalling the app, or `-seedSampleData` to seed a Debug build on a device. Seeded rows have fixed ids, so reinstalling against the same server never duplicates them. Grow the seed when a new feature's lists would start empty. Debug builds sync with the worktree's server using the bundled development token; the gym seed waits for the first sync, so run `bun run start:server`. Erase the app's data by uninstalling it (`xcrun simctl uninstall <udid> com.stefan.a-better-me`). The local database is `Library/Application Support/a-better-me/a-better-me.sqlite` in the app's data container; `sqlite3` can read the tables, the `_outbox` queue, and `_meta` (client id and cursor) directly.
- Regenerate the default gym equipment loads with `bun scripts/gym-defaults.ts`.
- Regenerate the exercise catalog with `bun scripts/catalog.ts`. It writes the bundled JSON under `Sources/App/Resources/Catalog/` and the downloaded images and Markdown under `Assets/`, then refreshes `Config/Assets.xcconfig`. Debug builds download them from the worktree's dev server, only when you tap the Assets row in More, so run `bun run start:server` and tap it to see them. Run `bun run assets upload` (needs AWS) before a Release build uses the new version; `bun run env:ios` also runs it. Regenerate fonts with `uv run --with fonttools python scripts/make-fonts.py <MF fonts dir> Sources/Shared/Resources/Fonts`.
- The dependencies are the sync engine's Swift package, `https://github.com/smirea/sync-engine` on branch `master` in `App.xcodeproj`, which brings GRDB (see `docs/decisions/sync.md`), sentry-cocoa, pinned exactly (see `docs/decisions/observability.md`), and Feedback, `https://github.com/smirea/feedback-engine` on branch `master`, the shake-to-feedback tool (see `docs/decisions/ios.md`). The launcher signs simulator builds ad hoc so the entitlements in `Config/App.entitlements` are embedded.
- Run the `AppTests` suites with `./scripts/test <Suite>` (several names, or none for all; `-t <udid>` picks another simulator; xcodebuild arguments go after `--`). It uses the worktree's simulator and `scripts/run`'s DerivedData, waits for room and a full boot, refreshes the owner's own packages as `scripts/run` does, builds, and installs the test host itself before xcodebuild launches it. It ends with the pass, fail, and skip counts, each failure, and the result bundle's path (`-- -resultBundlePath <path>` picks it), and exits 1 when no test ran, such as a misspelled suite. A plain `xcodebuild test` failed with "Simulator device failed to launch com.stefan.a-better-me. No such process" when the install ended a Live Activity an in-progress workout had started: `liveactivitiesd` launched the app in the background at the same moment as xcodebuild's suspended launch.
- There is no Swift package. The Xcode project is the only build: `xcodebuild build -project App.xcodeproj -scheme App -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO` checks compilation, and `./scripts/run -t simulator --no-watch` builds and launches it (add `--headless` as an agent).

# Design

- Follow the design language in `docs/decisions/design.md`. Before and after a UI change, run `./scripts/screen-tour --out <dir>` (pass the `agent-device` path `device_open` prints as `--agent-device` or `AGENT_DEVICE`) and pair the runs with `--compare`; add a new screen's tap path to `scripts/screen-tour.screens.ts`.
- Design for the owner's real volume, not the first week. Lists that grow with use (weigh-ins, food entries, past workouts, measurements, notes) reach hundreds of rows within a year, so check every screen against the seeded data and look for places where the amount of data hurts: a section that pushes the rest of the screen out of reach, a chart or summary buried under a raw list, a picker or menu with dozens of options, a long horizontal strip, repeated rows that would read better aggregated.
- A growing list inside a screen with other content is a `TruncatedList`: five and a half rows, the half row faded, and See All pushing a screen with every row. Never render an unbounded list inline. Prefer summarizing (averages, the latest value, a grouped count) over listing when the screen's job is an overview.

# Performance

Performance is a top priority: every tap must respond within a frame. Full rationale in [`docs/decisions/ios.md`](../docs/decisions/ios.md).

- Keep the main thread free of data work. Never read the database synchronously on main (`store.read`, an `@Observe` of a large query in a pushed view), never read files in `body`, and decode images off main at display size.
- `body` only lays out values that were already computed. Derive anything that loops over sessions, sets, the catalog, or Health samples once when its inputs change, in a shared store or in `@State`, never per render or per card.
- Fetch and decode the workout history once, in one app-level observer. Screens read from it; they don't each start their own `@Observe(WorkoutSession.finished)`.
- Keep invalidation narrow. Pass small `Equatable` values to child views, not closures, `Date.now`, or whole data bags, and assign `@Observable` properties only when the value changed.
- Avoid O(n²) work: a dictionary lookup instead of `first {}` or `contains {}` inside a loop, and SQL `WHERE` or `ORDER BY` instead of fetching everything and filtering in Swift.
- Judge speed only on a Release build on a device. Debug builds use `-Onone`. Sentry reports app hangs; check them after any change to a hot path.
- Cache what a row or card derives with `ViewMemo` (`DesignSystem/ViewMemo.swift`) in `@State`, keyed on every input it reads, so `body` only looks the value up. `TemplateSummary` caches each `WorkoutOverview` this way. A struct built in `body` from the history is the per-render work the rule above forbids.
- On the simulator, count work instead of timing it, since a Debug build's times mean little. `sample <pid> 5 -file out.txt` profiles the main thread during a gesture; the pid is the app's line in `xcrun simctl spawn <udid> launchctl list`, and it is a Mac process. To count re-renders, log from the suspect `body` or `init` with a temporary `Logger(subsystem: "probe", category: "probe")` and count lines in `xcrun simctl spawn <udid> log stream --predicate 'subsystem == "probe"'` while you drive the gesture. xctrace's SwiftUI and Time Profiler templates gave no usable trace on the simulator. Take the probes out before you commit.

# Environment

- When nested in `monorepo-swift`, this directory is an env-manager target of the root `.env`. Edit local values only in the root `.env.local` and run `env-manager gen --local` from either directory.
- Generated `Config/LocalSecrets.xcconfig` and `Config/Env.xcconfig` are ignored. `Config/Base.xcconfig` includes both; `Config/Info.plist` exposes `API_URL`, `OWNER_TOKEN`, `SENTRY_DSN_IOS`, the `ASSETS_*` asset settings, and the tracked `ASSETS_VERSION` to `AppEnvironment`. Debug's `ASSETS_URL` is the dev server's `$(API_URL)/assets`, with no credentials. Run `bun run env:ios` (needs AWS) before a Release build: it writes Release's production URL and token from env-manager `prod`.
- Saving generated configuration also triggers the launcher watcher. Native settings are bundled into the app, so keep server credentials out of the Swift target.
