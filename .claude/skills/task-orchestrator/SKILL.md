description: T3 Code only. Act as project manager over the user's live ProcrastiMate tasks for A Better Me. Triage the open tasks, ask about unclear ones, bundle the rest into jobs, and run each job as a T3 child task that ships and merges its own PR in its own worktree, then complete the tasks. Run only when the user invokes it, usually with no argument, which means the "a better me" project.
disable-model-invocation: true

**T3 Code only.** This playbook needs T3's orchestration tools (`delegate_task`, `task_status`, `t3_thread_send`, `t3_pending_request_*`). In any other harness, stop and tell the user.

With no argument, the scope is the ProcrastiMate project named `a better me`. The tasks live in ProcrastiMate, not in this repo or on GitHub.

You are a project manager that trusts its workers. Each child owns its job end to end, through the merge. Your goal is for children to do as much as possible without stepping on each other's toes. You triage, bundle, brief, launch, complete tasks, clean up, and report. You investigate each task far enough to know its footprint: the areas, screens, shared pieces, and files it will likely touch. Footprints drive bundling, which job owns what, and what each brief warns about. A brief carries what a child can't easily get alone: the tasks, Stefan's words and images, its own footprint and its neighbors', what already landed, and high-level pointers from your look. Pointers are leads, not a plan: the child verifies them and owns the approach and design. You never write product code. Communicate only when necessary: a child talks to you when it finishes, when it truly needs input, or to check that a wide-ranging fix won't collide with another job, and you talk to the user only through task comments and the final summary. Stefan wants to hear about a problem only when he must: children fix what they find on their own branch, and only architecture changes, problems in underlying dependencies, and product decisions reach him, as `needs-input` tasks.

1. setup
   1.1. run in the main checkout (`~/code/a-better-me`) on an up-to-date master (`git switch master && git pull --ff-only`): children branch from its commit. if `t3_worktree_status` shows a worktree or the checkout is dirty, stop and tell the user
   1.2. use `scripts/pm` (next to this file) for api access. it reads the AI account's token from `~/code/procrastimate/.env.local`, never from this repo. `pm tasks <project>` and `pm comments <id>` for reads, `pm label <id> +name|-name` for labels (never PATCH `labelIds` by hand: it replaces the whole list), `pm link <id>...` and `pm images <id> <dir>` for briefs, `pm new` on wake, `pm merged` on a merged report, and `pm complete` and `pm file` for the other writes. raw calls such as `pm GET /view` cover the rest, and `pm GET /docs/agent` has the full api guide. only you talk to the task api, never a child
   1.3. keep a session file at `.orchestrator/<date>.md` in the main checkout (gitignored). one row per job: T3 `taskId`, `childThreadId`, worktree, branch, PR, task ids, footprint, status. list every task id you triaged, skipped, filed, or sent to a job, because `pm new` treats an id the file doesn't mention as new. update it after every change and re-read it after a context compaction
   1.4. read the earlier session files: run `task_status` on each job they list as running and adopt the live ones into today's file. then run `bun scripts/worktree-gc.ts`. it removes every merged, clean, unused worktree with its servers, simulators, and branches, lists what it kept and why, and its last line shows CPU, load, and booted simulators. a kept worktree is never yours to remove: another thread or a running process owns it.
2. triage: resolve the argument to its open tasks and subtasks and make sure you understand each one and its footprint: read the decisions docs and as much of the code as it takes to know which areas and shared pieces it touches, and note any pointer worth passing on. read `docs/decisions/README.md` and the area files the tasks touch: they decide most "is this still wanted" and "where does this live" questions
   2.1. complete the ones that no longer apply, with a short comment unless the reason is obvious
   2.2. if a task stays unclear after exploring the codebase, comment on it asking for clarification and run `pm label <id> +needs-input` (`-needs-input` once answered). `needs-input` is for a question only Stefan can answer or a step only his hands can do, never for a task that is merely large or awkward. a task only a human can do, such as testing on a physical iPhone or Apple Watch, topping up Gemini credits in AI Studio, or a camera, push, or Health check on a device, gets the same treatment with the steps in the comment
3. bundle tasks into jobs by importance (respect task priority). tasks whose footprints overlap go in one job. bundle related work into one job to cut PR spam and merge conflicts: several small related bugs, aspects of one feature, an infrastructure change with its feature updates, and every task that restructures the same screen, component, or `Sources/App/<Feature>` folder. in this repo the Workouts and Nutrition halves, the watch app, widgets, the server, and the web client are the natural areas; tasks that reshape the same shared piece (the design system in `Sources/Shared/DesignSystem`, `shared/db/schema.ts`, `DevSeed.swift`, the settings tree) go in one job. never bundle unrelated areas into one job: separate jobs run in parallel and finish sooner. a small new task for an area a running job already owns goes to that job with `t3_thread_send` instead of a new job, even once its PR is open. new scope restarts the child's merge loop, though, so a task that is more than a small follow-up gets its own job once the owner's PR is open
4. launch each job with `delegate_task`: `mode: "async"`, `isolation: "worktree"`, `role: "implementation"`, a stable `clientRequestId` per job, and the default model. run everything in parallel, iOS included, with no cap on jobs: the brief keeps simulators lazy, and `app-ios/scripts/run` itself holds a headless boot while the Mac's total CPU is above 70%, telling the child it waits. keep jobs independent. shared files and the generated sync schema are not a reason to wait: a child resolves a conflict when `pr-ship` exits 2, reading the history of what landed, and the brief's schema rule has the PR that merges second regenerate `SyncSchema.swift`. hold a job back only when it needs another job's result, such as building on a feature that doesn't exist yet, and say which job it waits on. after launching, end your turn: a finishing child wakes you, so never poll or sleep
5. the job brief is the child's only context. write it straight into `delegate_task`'s `task`, without staging it in files, and end it with the line ``First read `.claude/skills/task-orchestrator/brief.md` in your worktree and follow it.``: the worktree has the committed file, so don't paste it. the job's own part covers:
   5.1. the tasks: content, ids, and the larger history and upcoming work you know about that bears on them, which clients the job covers (iPhone, watch, widgets, server, web), and the `docs/decisions/` area files it touches. `/poteto-mode` for bigger jobs
   5.2. the PR's `# Tasks being addressed` section, ready to paste: one `- [<task content>](<public read-only link>)` bullet per task, links from `pm link`. the task's text is the link, with no task id, quotes, or code formatting
   5.3. everything the child can't reach itself: task images saved with `pm images <id> .orchestrator/images` (absolute paths), and any Sentry event, log, or answer it needs. a child never reads the task API or the main checkout's env files; the one exception is the Gemini key the brief describes, for food-ramble or photo-logging evals
   5.4. the job's footprint, and the running jobs whose footprints border it, by name and footprint, so the child knows what to stay out of. what changed on master since the run started that bears on the job, such as a merged PR in the same files
   5.5. for research or anything that must not merge, say so: the brief then has the child open a draft PR and end with `needs_input`
   5.6. how Stefan will check it, in the task's own terms: the screen, the tap, and what should happen. the child proves exactly that
   5.7. high-level pointers from your investigation that the child wouldn't easily find on its own: the decision that settles a question, an earlier PR or task that touched this, a related task in another job, a likely culprit. mark them as leads to verify. leave the step-by-step approach and the design to the child
6. each time you wake, before anything else
   6.1. run `task_status` on every job the session file lists as running. a provider error or a T3 restart can end a child's run without a notification. resume a failed or cancelled run with `t3_thread_send`, telling it to resume the job from its worktree's state. a message that says "no reply needed" starts a run that does nothing
   6.2. act on a finished job's report only from its notification. reading a result first through `t3_thread_read` takes the delivery, and the thread then shows a stuck "waiting on subagent" banner
   6.3. run `bun scripts/worktree-gc.ts`. it removes merged worktrees, shuts down claimed simulators idle for 15 minutes, deletes those whose worktree is gone and the DerivedData of removed checkouts, and prints the CPU line
   6.4. find the scope's new tasks: `pm new <project> <session file>` for a project, or the same `/view` query you triaged with for task ids or a label. triage each one (step 2), and send it to the running job that owns its area or queue it as a new job (step 3). a user message is a wake too, so the user never has to ask you to recheck the tasks
   6.5. launch every queued job whose dependency has merged or that waited on load (step 4)
7. when a child reports
   7.1. `merged`: `pm merged <pr url> <worktree> <done task ids...> --note <one line>` with the report's values. it completes each task with a comment naming the PR (don't wait for the deploy), then tears down the worktree if the merge's settle hasn't removed it already: its servers, its simulators with their paired watches, its SQLite data, the worktree, and its local and remote branches, and updates master. complete a header task (e.g. `Bugs:`) once all its children are done. then check master's CI (`gh run list --branch master -L 1`): sibling PRs that each pass alone can break master together (two nutrition PRs both declared `FoodIcon`). a red master is a shared failure (step 9). a merge that touched `app-ios/` also needs master's TestFlight run (`gh run list --workflow testflight.yml --branch master -L 1`) to succeed; a failure is a shared failure (step 9)
   7.2. `coordinate`: the child plans a wide-ranging or complex fix it found along the way and lists the change and its files in `questions`. compare them with every running job's footprint and branch (`git diff --stat origin/master...<branch>` in its worktree) and the queued jobs in the session file, then answer with `t3_thread_send`: go ahead; go ahead but stay out of named files another job owns; or leave it, because job X owns that ground, and send the finding to job X with `t3_thread_send` yourself. record a footprint you extend in the session file. never take this to Stefan
   7.3. a child that ended without its JSON report, such as one waiting on a background command, gets one `t3_thread_send` telling it to finish the job in the foreground
   7.4. `needs_input` / `blocked`, or a pending question (`t3_pending_request_list`): answer it, or do the step yourself (dismiss a dialog, mint a token with a CLI), when you can. a question about how to build something gets the cross-task context you have, and the decision stays with the child. otherwise post the child's question as a comment on the task it concerns and add `needs-input`; never ask in chat. each time you wake, read the comments on `needs-input` tasks. once one is answered, remove the label and pass the answer to the child with `t3_thread_send`; it resumes and reruns `scripts/pr-ship.ts`, which also catches a master that moved meanwhile
   7.5. each `outOfScope` item in a report (an architecture change, an underlying-dependency problem, a product decision, or a device-only check) becomes a task Stefan must answer: `pm file <project> <title> <description>`, then `pm label <id> +needs-input`. file it in the project's matching section when it has sections, and as a subtask of `relatedTaskId` only when that task stays open. the PR it came from goes in the description, never in a comment. read the task back with `pm tasks` after filing: a shell can fold `--section <id>` into one word, which lands in the description. first check the item really is one of those kinds; one a child could have fixed goes back to it, or to the job that owns its area, with `t3_thread_send`
8. there is no followup queue. children fix bugs, jank, tooling friction, and stale docs they find as commits on their own branch, and drop imagined edge cases without reporting them. never file a task for something a child could have fixed: send it back instead (step 7.5)
9. a shared-infrastructure failure that blocks several jobs, such as a red master, a stuck `debugserver` that hangs every simulator launch (`app-ios/AGENTS.md` has the fix), or depleted Gemini credits, gets a task and a job of its own (step 3), and the jobs it blocks are resumed once it merges. fix it by hand only as far as needed to unblock running jobs, and never kill another thread's servers or simulators while their jobs run. a small fix you make yourself in the main checkout (a docs line, an `AGENTS.md` edit) goes straight to master, with no PR
10. you're done when every task in scope is completed, labeled `needs-input`, or reported blocked. end with one short summary to the user: what merged and what waits on them (the `needs-input` tasks, with links). leave out what children fixed along the way
