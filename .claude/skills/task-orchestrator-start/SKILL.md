**T3 Code only.** This playbook needs T3's orchestration tools (`delegate_task`, `task_status`, `t3_thread_send`, `t3_pending_request_*`). In any other harness, stop and tell the user.

With no argument, the scope is the ProcrastiMate project named `a better me`. The tasks live in ProcrastiMate, not in this repo or on GitHub.

You are a project manager that trusts its workers. Each child owns its job end to end, through the merge. You never write product code yourself: you triage, brief, launch, complete tasks, clean up, and report. Communicate only when necessary: a child talks to you once, when it finishes or truly needs input, and you talk to the user only through task comments and the final summary.

1. setup
   1.1. run in the main checkout (`~/code/a-better-me`) on an up-to-date master (`git switch master && git pull --ff-only`): children branch from its commit. if `t3_worktree_status` shows a worktree or the checkout is dirty, stop and tell the user
   1.2. use `scripts/pm` (next to this file) for api access. it reads the AI account's token from `~/code/procrastimate/.env.local`, never from this repo. `pm tasks <project>` and `pm comments <id>` for reads, `pm label <id> +name|-name` for labels (never PATCH `labelIds` by hand: it replaces the whole list), `pm link <id>...` and `pm images <id> <dir>` for briefs, `pm new` on wake, `pm merged` on a merged report, and `pm complete` and `pm file` for the other writes. raw calls such as `pm GET /view` cover the rest, and `pm GET /docs/agent` has the full api guide. only you talk to the task api, never a child
   1.3. keep a session file at `.orchestrator/<date>.md` in the main checkout (gitignored). one row per job: T3 `taskId`, `childThreadId`, worktree, branch, PR, task ids, status. list every task id you triaged, skipped, filed, or sent to a job, because `pm new` treats an id the file doesn't mention as new. update it after every change and re-read it after a context compaction
   1.4. read the earlier session files: run `task_status` on each job they list as running and adopt the live ones into today's file. then run `bun scripts/worktree-gc.ts` (its `Load` line shows load, booted simulators, and worktrees), and tear down each merged worktree it lists that an earlier session file names (`bun scripts/teardown-worktree.ts <worktree>`). leave merged worktrees no session file names; another thread owns them. `~/.claude/orchestrate/` holds an older, different coordinator's state (the nutrition program); read it for history, never write to it
2. triage: resolve the argument to its open tasks and subtasks and make sure you understand each one. read `docs/decisions/README.md` and the area files the tasks touch: they decide most "is this still wanted" and "where does this live" questions
   2.1. complete the ones that no longer apply, with a short comment unless the reason is obvious
   2.2. if a task stays unclear after exploring the codebase, comment on it asking for clarification and run `pm label <id> +needs-input` (`-needs-input` once answered). a task only a human can do, such as testing on a physical iPhone or Apple Watch, topping up Gemini credits in AI Studio, or a camera, push, or Health check on a device, gets the same treatment with the steps in the comment
3. bundle tasks into jobs by importance (respect task priority). bundle related work into one job to cut PR spam and merge conflicts: several small related bugs, aspects of one feature, an infrastructure change with its feature updates, and every task that restructures the same screen, component, or `Sources/App/<Feature>` folder. in this repo the Workouts and Nutrition halves, the watch app, widgets, the server, and the web client are the natural areas; the design system (`Sources/Shared/DesignSystem`), `shared/db/schema.ts`, `DevSeed.swift`, and the settings tree are shared, so a task that reshapes one of them gets one job and the jobs that use it wait or are told. never bundle unrelated areas into one job: separate jobs run in parallel and finish sooner. a small new task for an area a running job already owns goes to that job with `t3_thread_send` instead of a new job, even once its PR is open. new scope restarts the child's merge loop, though, so a task that is more than a small follow-up gets its own job once the owner's PR is open
4. launch each job with `delegate_task`: `mode: "async"`, `isolation: "worktree"`, `role: "implementation"`, a stable `clientRequestId` per job, and the default model. run everything in parallel by default, iOS included. the brief keeps simulators lazy, so only a job that has to look at the app boots one. hold new launches while the gc `Load` line's first number is above three times the core count, or while more than three simulators are booted (the nutrition run stalled at six), and launch them on a later wake. shared files and the generated sync schema are not a reason to wait: a child rebases when `pr-ship` exits 2, and the brief's schema rule has the PR that merges second regenerate `SyncSchema.swift`. hold a job back only when it needs another job's result, such as building on a feature that doesn't exist yet, and say which job it waits on. after launching, end your turn: a finishing child wakes you, so never poll or sleep
5. the job brief is the child's only context. write it straight into `delegate_task`'s `task`, without staging it in files, and end it with the line ``First read `.claude/skills/task-orchestrator-start/brief.md` in your worktree and follow it.``: the worktree has the committed file, so don't paste it. the job's own part covers:
   5.1. the tasks: content, ids, and the larger history and upcoming work you know about that bears on them, which clients the job covers (iPhone, watch, widgets, server, web), and the `docs/decisions/` area files it touches. `/poteto-mode` for bigger jobs
   5.2. the PR's `# Tasks being addressed` section, ready to paste: one `- [<task content>](<public read-only link>)` bullet per task, links from `pm link`. the task's text is the link, with no task id, quotes, or code formatting
   5.3. everything the child can't reach itself: task images saved with `pm images <id> .orchestrator/images` (absolute paths), and any Sentry event, log, or answer it needs. a child never reads the task API or the main checkout's env files; the one exception is the Gemini key the brief describes, for food-ramble or photo-logging evals
   5.4. the running jobs whose areas border this one, by name and area, the top-level Swift types and settings keys they add when you know them, and what changed on master since the run started that bears on the job, such as a merged PR in the same files
   5.5. for research or anything that must not merge, say so: the brief then has the child open a draft PR and end with `needs_input`
6. each time you wake, before anything else
   6.1. run `task_status` on every job the session file lists as running. a provider error or a T3 restart can end a child's run without a notification. resume a failed or cancelled run with `t3_thread_send`, telling it to resume the job from its worktree's state. a message that says "no reply needed" starts a run that does nothing
   6.2. act on a finished job's report only from its notification. reading a result first through `t3_thread_read` takes the delivery, and the thread then shows a stuck "waiting on subagent" banner
   6.3. run `bun scripts/worktree-gc.ts`. it prints the `Load` line, booted simulators no worktree owns, and merged worktrees still waiting for teardown. it shuts nothing down; a booted simulator named after a finished job's branch gets torn down with that job
   6.4. find the scope's new tasks: `pm new <project> <session file>` for a project, or the same `/view` query you triaged with for task ids or a label. triage each one (step 2), and send it to the running job that owns its area or queue it as a new job (step 3). a user message is a wake too, so the user never has to ask you to recheck the tasks
   6.5. launch every queued job whose dependency has merged or that waited on load (step 4)
7. when a child reports
   7.1. `merged`: `pm merged <pr url> <worktree> <done task ids...> --note <one line>` with the report's values. it completes each task with a comment naming the PR (don't wait for the deploy), then tears down the worktree from the main checkout: its servers, SQLite data, worktree, branches, and the simulator named after the branch, and updates master. complete a header task (e.g. `Bugs:`) once all its children are done. then check master's CI (`gh run list --branch master -L 1`): sibling PRs that each pass alone can break master together (two nutrition PRs both declared `FoodIcon`). a red master is a shared failure (step 9). tell each running job that borders the merged one, with `t3_thread_send`, what landed
   7.2. a child that ended without its JSON report, such as one waiting on a background command, gets one `t3_thread_send` telling it to finish the job in the foreground
   7.3. `needs_input` / `blocked`, or a pending question (`t3_pending_request_list`): answer it yourself when you can. otherwise post the child's question as a comment on the task it concerns and add `needs-input`; never ask in chat. each time you wake, read the comments on `needs-input` tasks. once one is answered, remove the label and pass the answer to the child with `t3_thread_send`; it resumes and reruns `scripts/pr-ship.ts`, which also catches a master that moved meanwhile
   7.4. a child that adds a setting reports `needs_input` with the variable, its schema line, and which environments need a value, because only the main checkout may run `env-manager up`. do it yourself: note master's SHA, copy the PR's `.env` into the main checkout, add the value to `.env.local`, `env-manager up` for `dev`, then `env-manager env set prod`, the same for `prod`, and `env-manager env set dev`. `up` and `env set` each make a local "chore: env manager update" commit and refuse while `.env.override` holds a key the schema lacks: move `.env.override` aside for the upload, put it back, and `git reset --hard <sha>` afterwards; never push those commits. a server secret also goes on the Worker before the merge: run `bun scripts/secrets.ts push` from the child's worktree, since CI's `secrets verify` fails the deploy without it. then tell the child to continue
   7.5. file every followup with `pm file <project> <title> <description>`, in the project's matching section (`Bugs` for bugs) when it has sections, as a subtask of `relatedTaskId` only when that task stays open. the PR it came from goes in the description, never in a comment. read the task back with `pm tasks` after filing: a shell can fold `--section <id>` into one word, which lands in the description. dev-tooling friction a child reports (a slow command, a flaky tool, a manual step) goes to a GitHub issue with `gh issue create` instead, per `AGENTS.md`
8. work the followups in the same run: each new followup is a task in scope, so bundle and launch it like any other (step 3). file but don't launch a followup that costs more than it's worth, such as a rare edge case or a bug in another repo (`sync-engine`, `env-manager`), and say why in the summary
9. a shared-infrastructure failure that blocks several jobs, such as a red master, a stuck `debugserver` that hangs every simulator launch (`app-ios/AGENTS.md` has the fix), or depleted Gemini credits, gets a task and a job of its own (step 3), and the jobs it blocks are resumed once it merges. fix it by hand only as far as needed to unblock running jobs, and never kill another thread's servers or simulators while their jobs run. a small fix you make yourself in the main checkout (a docs line, an `AGENTS.md` edit) goes straight to master, with no PR
10. you're done when every task in scope, followups included, is completed, labeled `needs-input`, reported blocked, or filed and skipped with a reason. end with one summary to the user: what merged, what waits on them, the followups you skipped and why, and the GitHub issues you opened
