# Live workout surfaces

The in-progress workout shows in three places besides the phone's live editor: the Apple Watch app, the Live Activity on the Lock Screen and in the Dynamic Island, and Apple Health, which records it. The reference app's versions are captured in [`docs/research/mf-workouts/watch.md`](../research/mf-workouts/watch.md).

## One store, one contract

- **The phone's database is the only store; the watch runs workouts on its own.** Once a workout starts, the watch needs nothing from the phone: it can start one, log every set, rest, pause, and finish with the phone in a locker or switched off. It does that on a `WatchWorkout`, the session's blocks plus everything the phone would look up to log a set, and turns each action into a `WatchEvent` that it applies at once and queues for the phone. The phone applies the events to the stored session whenever they arrive, with the times the owner acted, so the database stays the one record and a set logged offline keeps its real time. MF's watch is a standalone host too, but edits a second copy and resolves conflicts by instance id and diff date ([research §2.1](../research/mf-workouts/watch.md)); replaying events instead needs no merge, because each event names its row and applying it twice converges. The Live Activity has no copy at all: it renders a `LiveWorkoutSnapshot` and sends `LiveWorkoutCommand`s back.
- **`LiveWorkoutController` is the seam.** `Sources/App/Workouts/Live/LiveWorkoutController.swift` observes the in-progress session, the settings, the earlier sessions behind the Previous column, and `LiveSessionStore`, and rebuilds `status` for the Live Activity and `watchWorkout` for the watch whenever any of them change. The Live Activity calls `perform` with commands and the watch's events go through `apply`. Nothing else in the session code knows the watch or the Live Activity exist.
- **The status is what the phone would do next.** `current` is the row the phone would log next (the current exercise's first open row, else the next unfinished exercise's), with the values it would log: the typed draft, else the Smart Progression or Previous prefill. `upNext` is the row that follows once `current` is logged, found by running the same `SessionFlow.afterCompleting` rules the check button runs. `pauseAdjustedStart` is the start moved forward by finished pauses, so `Text(timerInterval:)` draws the workout clock.
- **Commands go through the editor while it is on screen.** The editor holds the session's blocks in its own state and writes them through, so a second writer would race it. While it is up it registers `perform(_:)`, and a log from the watch runs the same `toggle` as a tap: Apply in session, rest, and auto-scroll included. With the editor closed the controller applies the command to the stored session with the same `SessionFlow` functions. Smart Progression's suggestions live in the in-memory `LiveSessionStore`, so until the editor has opened once in this launch the closed path prefills from Previous values.
- **Every command names the row it was shown.** `log`, `unlog`, and `edit` carry the row's id, so a tap that crosses a change on the phone acts on the row the owner saw, and does nothing once that row is gone or already logged.
- **Finishing remotely is Done without a plan update.** `finish` keeps the logged sets, leaves open rows unlogged, ends the session, and advances the program, like Workout Complete's Done with Update Workout Plan off. The phone's live cover closes because the session is no longer in progress.

## Targets and shared code

- **Three targets share one folder.** `Sources/App` is the iPhone app, `Sources/Watch` the watchOS app (`com.stefan.a-better-me.watchkitapp`, embedded in the iPhone app), and `Sources/Widgets` the widget extension that draws the Live Activity (`com.stefan.a-better-me.widgets`). `Sources/Shared` is compiled into all three: the design tokens and fonts, `WeightUnit`, `SetType`, and the live workout contract in `LiveWorkout.swift`. Every folder is a synchronized group, so new files need no project edits.
- **The contract only grows.** `LiveWorkoutStatus`, `LiveWorkoutCommand`, `WatchWorkout`, and `WatchEvent` are Codable values sent between devices that may run different builds for a moment, so fields are added as optionals and cases are added, never renamed.
- **The Live Activity carries only the status.** ActivityKit caps a content state at 4 KB, so `WorkoutActivityAttributes.ContentState` is `LiveWorkoutStatus`.
- **The app group is `group.com.stefan.a-better-me`.** The app and the widget extension share it for anything the Live Activity draws that doesn't fit in the content state. The app writes the current and up-next exercises' first frame there as a 120 px square JPEG (`Thumbnails/<catalog id>.jpg`) before it updates the activity; exercises without a frame show their initials.

## Live Activity

- **`WorkoutActivityController` mirrors the status.** `Sources/App/Workouts/LiveActivity/` observes `status` and calls ActivityKit only when the status changed. It requests the activity when a session is in progress, adopts the session's activity left by an earlier launch, and ends any other. ActivityKit refuses a request from the background, so the controller asks again each time the app becomes active, which covers a launch into a running session and a session started from the watch while the phone was locked.
- **Ending shows the finished banner for a minute.** When the session leaves the status, the controller reads it back: a finished session ends the activity with its last status plus `endedAt` (duration and sets logged) and dismisses it after 60 seconds; a discarded one disappears at once.
- **A rest's content goes stale when the rest ends.** A suspended app can't clear an expired rest, so each update sets `staleDate` to the rest's end, and the widget draws the set instead of the rest once `isStale` is true. The iOS 27 simulator never redrew at the stale date, so there the banner holds 0:00 until the app runs again: any button press (Skip on an expired rest just moves to the set) or opening the app. On a phone, the workout's `HKWorkoutSession` keeps the app running, so the rest's end updates the activity directly.
- **One intent carries every button.** `LiveWorkoutIntent` (`Sources/Shared/LiveActivity/`) holds a JSON-encoded `LiveWorkoutCommand`. It is a `LiveActivityIntent`, so it runs in the app's process, where `WorkoutActivityController` installs its handler at launch. The handler waits up to a second for the change to reach the activity, since the process may be suspended once `perform` returns.
- **The buttons map MF's onto the command set.** Complete set sends `log` with the shown values (MF's Next), skip sends `skipRest` (MF's Next during rest), −15 and +15 send `adjustRest`, and pause and resume take the slot of MF's Previous. Previous is cut: it would `unlog` the last logged row, which the status does not name, and an accidental tap on a locked phone would undo a set. MF's End opens the app; here the Finish button (shown once every set is logged) and a tap anywhere on the activity open `abetterme://workout/live`, which expands the live workout, so finishing always runs Workout Complete on the phone.
- **The Dynamic Island mirrors the banner.** Compact shows the exercise thumbnail and the workout clock, or a timer glyph and the rest countdown. Minimal shows the rest countdown or a dumbbell. Expanded holds the thumbnail, the heading, the clock or countdown, and the banner's controls row; during a rest that row trades pause for −15 and +15, since the island has no room for the banner's rest header.

## Watch app

- **Two transports, one message type.** `Sources/Shared/Watch/WatchMessage.swift` is everything the phone and watch say to each other, Codable and only growing like the contract. In a workout it rides the mirrored `HKWorkoutSession`'s data channel; otherwise WatchConnectivity carries it: `sendMessage` when the other side is reachable, queued `transferUserInfo` for what must arrive (the watch's events, the finished workout, the saved summary), and the application context always holds the latest home list and workout, so a watch app that opens later starts from them. `WatchBridge` (`Sources/App/Workouts/Health/`) is the phone's end and `WatchModel` (`Sources/Watch/`) the watch's.
- **Either side asks again after a gap.** A `sendMessage` to an unreachable watch is dropped, so the phone resends the home list and workout whenever the watch becomes reachable, and the watch sends `hello` each time it becomes active. The phone updates the application context without checking `isWatchAppInstalled`, which read false for seconds at a time between paired simulators while the app was installed; a skipped update had left the watch on an old set.
- **The data channel is used only once proven.** `startMirroringToCompanionDevice()` returns without error even when the phone is out of reach: the watch's healthd queues the mirror and retries every 5 s. Simulators never deliver it, because healthd sends the mirror over Rapport, which has no `PairedCompanion` between simulators (`RPErrorDomain -6727`, "Remote device is unreachable"; Apple DTS confirms [mirroring is unsupported in simulators](https://developer.apple.com/forums/thread/765469)), while WatchConnectivity and Health sync ride a mock IDS link that works. So the mirror path can only be tested on a real iPhone and watch. The watch therefore sends over the channel only after a message arrives on it, and announces its recording with `recordingStarted` over WatchConnectivity. Without a mirror the watch also sends its heart rate and energy as `stats` every 5 s, so the phone and its Live Activity still show them.
- **The watch keeps the phone's copy and its own outbox.** `WatchReplica` (`Sources/Shared/Watch/WatchWorkout.swift`) is the workout as the phone last sent it, or as the watch started it, plus the events the phone hasn't acknowledged; the watch shows the copy with the outbox applied, and saves both to disk so a relaunch mid-workout resumes. Each event goes out as queued user info, which WatchConnectivity delivers in order even after the app is suspended, and the whole outbox is resent as a message whenever the phone is reachable. The phone skips events it already applied, keeping the last 500 acknowledged ids across launches so a resent pause and resume or rest change never counts twice, and acknowledges an event only once its rebuilt copy shows it, since an acknowledgment that outran the database write let the watch drop an Undo while the copy it received still predated it. The watch folds acknowledged events into its copy before dropping them, so it never loses state the phone confirmed. Each batch the watch sends is answered at once with the acknowledged ids among the ones it sent. An event for the live session takes the same paths as the phone's own controls, with the open editor using the event's time for the log and the rest; one for any other session, such as a workout the watch started while the phone had its own in progress, goes straight to that row, so both workouts are kept. WatchConnectivity delivers queued copies late and in order, so a copy of a different workout replaces the watch's only when it is newer and still in progress; a late copy of an older finished workout had cleared the summary of the one just done. After a finish the phone keeps sending the finished copy rather than none, so a watch that hears the latest message first still sees the end, saves its recording, and shows the summary.
- **The home list carries a ready plan per workout.** The phone publishes the program's next workout, then the library, whenever templates, the active program, or the history change, each with a `WatchWorkout` as it would start now: the gym's loadable weights, rest, and prefill and previous values from the history. Start runs that plan on the watch with a new session id, and its `start` event makes the phone insert the same session with the same row ids, as a program day when it is one. About ten workouts fit in 10 KB of application context.
- **Screens follow MF's renders.** A paged workout view: controls, the current set or rest, and stats. The set screen shows the exercise, a superset member's letter, the exercise's sets as dots with W, D, F, and M badges, the set type, and weight, reps, and RIR pills, with last time's log under them; tapping the exercise opens the exercise list. Tap a pill and turn the Digital Crown to change it: weight steps through what the exercise's equipment loads in the session's gym (the same `Loading.of` the editor's stepper uses), else 2.5 lb or 1.25 kg, and RIR runs 0 to 6+ in its zone color. A full-width Log Set button logs it, then the same `SessionFlow` rules as the phone pick the rest and the next row: superset members alternate with no rest until the round ends, drops follow their set, and auto-next moves on. Rest is a draining ring around a big countdown with −15 s, skip, and +15 s, the next set under it, a tap on the wrist 10 s before the end and a stronger one at the end. Controls has pause or resume, end (Finish & Save or Discard), Undo of the last logged set, Add Set, and the exercise list; stats has the workout clock, heart rate with its zone, active energy, and progress. The finish screen shows duration, sets, volume, and the Health numbers once saved. Black background with a glow from the bottom (lavender while resting, green when done) that dims in Always On, DM Sans.
- **Heart rate zones are shares of 220 minus age.** Five zones, below 60% then one per 10% of maximum heart rate. Age comes from Health's date of birth; without it the watch assumes 30. MF's Karvonen option and heart-rate rest exits are cut.
- **Agents drive the watch with `scripts/watch-drive`.** T3's device tools list no watch simulators, so `app-ios/scripts/watch-drive <watch-udid> start` runs `UITests/Watch/WatchDriver` as a long-lived UI test, and every other command (`tap`, `crown`, `swipe`, `shot`, `tree`, `systree`, `systap`) is a file it answers. `systap com.apple.Carousel` reaches system sheets such as Health access, so the watch's grant is given through the real sheet. Starting the driver boots the paired iPhone, so a test with the phone away shuts the phone simulator down after the driver is up. The Darwin-notification hooks it replaced are gone. `./scripts/run` installs the embedded watch app on the simulator's paired watch, launches the phone app, then relaunches the watch app until the watch's WatchConnectivity daemon links it to the phone app. After a fresh `simctl install` that link arrives only once the phone app has activated its session, and a watch app launched before it never activates its own (`wcd` logs a client with no communication ID), so it hears nothing from the phone until relaunched. A watch app installed through the iPhone has the link from the start.

## Apple Health

- **The device that runs the workout session records it.** When a paired watch has the app, starting a workout on the phone calls `startWatchApp(toHandle:)`, and the watch app starts an `HKWorkoutSession` mirrored to the phone, so heart rate and energy come from the watch's sensors. The phone waits up to 10 s to hear from the watch (a mirror or `recordingStarted`) and otherwise runs its own `HKWorkoutSession`, which reads heart rate from any connected sensor; without the watch app it starts right away. If the watch speaks up within a minute of the phone beginning to record, the phone discards its own copy: the watch measures heart rate and stays with the owner when the phone is left behind. Later the watch discards its copy instead, since it would only cover the rest of the workout. A workout started on the watch is recorded there from its first second, and the phone never starts one for it, also after a relaunch (it keeps those session ids). A watch-started workout whose recording fails to start, such as with Health access denied, is not recorded anywhere. Either way exactly one session records each workout. `WorkoutHealth` (`Sources/App/Workouts/Health/`) follows the in-progress session through `LiveWorkoutController.status`: a new session starts recording, a pause pauses it, an ended row saves it, and a deleted row discards it.
- **What a workout records.** Traditional strength training, indoor, with the builder's heart rate, active and basal energy, and pause and resume events. One segment event per exercise with a logged set: only completion times are logged, so a segment runs from the last set of anything before the exercise's first set (or the start) to its own last set, and superset members overlap. Metadata holds the workout name (`BetterMeWorkoutName`), and each segment its exercise (`BetterMeExercise`). The recording device saves it as soon as the workout ends, here or on the phone, with a `WorkoutRecordingPlan` (end, name, segments, effort) that `HealthRecordingPlan` works out from the logged sets; the watch has them in its own copy. After a relaunch the watch takes back the session HealthKit kept running, and starts a new one for the rest of the workout when none survived.
- **Effort comes from RIR.** The workout's effort score is 10 minus the working sets' average logged RIR, rounded and clamped to 1-10: all sets at failure is 10, two in reserve is 8. Warm-ups don't count, and with no logged RIR there is no score. It is related to the workout with `relateWorkoutEffortSample`, so Fitness shows it with the workout.
- **A saved workout is summarized on its session.** `workout_sessions.health` holds a `WorkoutHealthSummary`: the `HKWorkout` UUID, the recording device, average and max heart rate, and active and total energy. It syncs like the rest of the row, so the history keeps those numbers without asking Health, and a later key needs no migration. Workout Complete shows them, or the live numbers until the save lands, and live heart rate and active energy also feed `LiveWorkoutController.metrics` for the Live Activity.
- **Saving is idempotent.** The workout uses the session id as its `HKMetadataKeySyncIdentifier` with version 1, so a retry after a crash replaces the same workout instead of adding a second one.
- **Each device asks for Health access only when the owner acts on it.** The phone asks when a workout starts. The watch asks when the owner taps Start on it or the phone launches it to record, never at launch, and finds access already settled when the phone asked first. The phone app and its watch app share one grant that Health syncs between the two. The watch used to ask at launch, and its sheet sat unanswered until a workout relaunched the app; Health stored that dismissal as a newer decision, synced it to the phone, and revoked the grant the owner had just given there, so both devices failed to record with "Not authorized".
- **No Health settings yet.** Recording is always on once Health access is granted; the authorization sheet appears when the first workout starts. MF's separate "save workouts" and "record live session" switches are cut until someone wants them off.
