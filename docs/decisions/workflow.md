# Workflow

- **One PR per thread, never stacked.** Fold small same-area follow-ups into an open PR instead of starting a new thread.
- **Rebase only on a real conflict.** PR CI already tests the merge with `master`.
- **Every agent worktree is sandboxed by script.** `bun scripts/setup-worktree.ts [branch]` installs, gives the worktree its own ports, and writes offline env files; the server's SQLite file lives inside the worktree, so nothing else is shared ([Sync](sync.md)). T3 Code runs it as the project's blocking setup script, so an agent starts in a ready worktree. `bun scripts/teardown-worktree.ts <worktree | branch>` stops its servers and removes the worktree, its data, and its branches from the main checkout once the PR is merged. Rules that a script can enforce live in the script, not in prompts.
- **PRs wait on one script.** `bun scripts/pr-ship.ts [--merge]` waits for CI, lists failing checks and unresolved review threads, reports a conflict with master, and merges when green. It exits before the 600-second tool limit with a code that names the next step, printed as its last line, so an agent reruns it instead of writing `sleep` loops.
- **Hooks run only what the change touches.** Pre-commit runs oxlint and oxfmt one after the other on staged files, since in parallel one overwrote the other's fix. `bun check` (Bun's TypeScript 7 checker, 3-4x faster than `tsc`) runs only when a script or JSON file is staged. Pre-commit and pre-push run `scripts/test-changed.ts`, which picks every test whose imports reach a changed file. It runs with `--no-env-file`, so it sees the same environment as CI.
- **Tests run in a pinned zone on in-memory SQLite.** `bunfig.toml` preloads `scripts/test-timezone.ts`, and the server tests open their own `bun:sqlite` space, so no test can reach shared data.
- **Git hooks are never skipped.** A Claude Code hook in `.claude/settings.json` blocks `--no-verify` and lefthook overrides. A failing hook gets its cause fixed; a flaky test is a bad test.
- **Run only the relevant tests locally.** CI runs the full suite.
- **Friction gets fixed or filed.** Development speed is a goal in itself. An agent that hits a manual step, a repeated prompt, a slow command, or a flaky tool fixes it in the same thread when the fix is small, and otherwise opens a GitHub issue with its findings and a proposed fix (as with [#84](https://github.com/smirea/a-better-me/issues/84), HealthKit on fresh simulators).
- **Environments start on the default path.** The common case is the owner using the app with everything allowed and real-looking data, so simulators get every permission granted (after a fresh install `scripts/run` runs `UITests/App/PermissionsGrant`, which answers the app's launch-time Health sheet and system prompts) and Debug builds seed their data. `simctl privacy grant all` is not used: it also resets the app's Health access, which made the sheet return on every run. Testing a denied, limited, or empty state is the exception: the agent revokes the permission or clears the data for that test.
- **Apple Health is off in Debug simulator builds.** The one exception to the default path. Health's sheet kept stopping agents after the grant above: an existing simulator never reran it, and every new Health type asks again on every simulator. Most work never touches Health, and the seeded app weigh-ins and imported steps still fill the Dashboard. So `HealthStore.isAvailable` is false there, and the app takes the path it takes when Health is denied. An agent working on Health runs `scripts/run --health on`, which persists in the app's defaults and answers the sheet; `--health off` turns it off again. Release builds and Debug builds on a device always use Health, and the watch app is not gated.
- **Large features run as one coordinator and several worker threads.** The coordinator thread lands the shared groundwork (types, persistence, design system, shared data) in its own PR first. Then it launches one T3 Code worker thread per feature, each in its own worktree branched from `master` and owning a disjoint set of folders listed in the area's decision file. A worker that must change a shared file says so in its PR description, and the coordinator resolves overlaps. Each worker verifies its features in its own simulator, headless through T3 Code's device tools unless the user is watching, ends its `agent-device` session and shuts the simulator down with `device_close` when done, and babysits its own PR to merge with `pr-ship --merge`. The coordinator tells running workers when a sibling PR lands, and integrates across features after the merges. Worker threads use `t3_thread_launch` with a `worktree` workspace strategy, so T3 runs `scripts/setup-worktree.ts` before the agent starts.
- **Reference-app research is serialized.** Only one agent can drive a reference app's window at a time. Research runs before the feature workers start and lands as a spec with screenshots under `docs/research/`, which the workers read instead of driving the app.

## Worktree storage

- T3 generates a descriptive branch name concurrently with setup. Never pass a branch name to setup in a T3-owned worktree or rename its branch from a setup/teardown hook. Resource identity follows the worktree directory, not the branch name.
- On this Mac, T3 runs `worktree-cache-clean` from the shared scripts repository when a thread settles. It removes only wholly ignored Xcode `DerivedData` directories in linked worktrees, independently of whole-worktree retention. It preserves source, uncommitted files, env files, and databases, and skips worktrees with running T3 turns or open build files. Main checkouts are never cleaned. The next build regenerates the output.
- Native launchers reuse `DerivedData/SourcePackages` within each checkout; device and simulator compilation outputs remain separate. Do not create ad hoc `check`/`test` package caches: pass `-clonedSourcePackagesDirPath app-ios/DerivedData/SourcePackages` when running `xcodebuild` from the repository root. Each worktree keeps its own package directory so parallel tasks do not mutate another checkout's dependencies.
- Branch metadata mismatches can still block T3's whole-worktree cleanup. Repair ownership through T3 rather than force-removing a potentially live checkout; build-cache cleanup does not depend on the saved branch name.
