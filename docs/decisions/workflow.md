# Workflow

- **One PR per thread, never stacked.** Fold small same-area follow-ups into an open PR instead of starting a new thread.
- **Rebase only on a real conflict.** PR CI already tests the merge with `master`.
- **Every agent worktree is sandboxed by script.** The worktree lifecycle is shared with the owner's other repos, in `agent-t3-worktree` and `agent-simulator` from `~/code/scripts`; this repo keeps only proxies with the old names. T3 Code runs `agent-t3-worktree setup` when it creates a worktree: it installs, gives the worktree its own ports, and writes offline env files; the server's SQLite file lives inside the worktree, so nothing else is shared ([Sync](sync.md)). A Claude Code session-start hook and pre-commit run `agent-t3-worktree check --heal`, so a worktree whose setup is missing or stale heals itself and no agent runs setup by hand. When a thread settles, which merging its PR does, `agent-t3-worktree settle` stops its servers and simulators and removes merged worktrees with their data, simulators, and branches. `bun scripts/worktree-gc.ts` does the same for every merged worktree of this repo, and `bun scripts/teardown-worktree.ts <worktree | branch> [--force]` removes one. Rules that a script can enforce live in the script, not in prompts.
- **PRs wait on one script.** `bun scripts/pr-ship.ts [--merge]` waits for CI and for Codex's first review (`chatgpt-codex-connector` reviews every PR on its own when it opens, so nobody requests one), lists failing checks and unresolved review threads, reports a conflict with master, and merges when green. It exits before the 600-second tool limit with a code that names the next step, printed as its last line, so an agent reruns it instead of writing `sleep` loops.
- **Hooks run only what the change touches.** Pre-commit first runs the worktree check above, then the rest in parallel: oxlint and oxfmt one after the other on staged files, since in parallel one overwrote the other's fix. `bun check` (Bun's TypeScript 7 checker, 3-4x faster than `tsc`) runs only when a script or JSON file is staged. Pre-commit and pre-push run `scripts/test-changed.ts`, which picks every test whose imports reach a changed file. It runs with `--no-env-file`, so it sees the same environment as CI.
- **Tests run in a pinned zone on in-memory SQLite.** `bunfig.toml` preloads `scripts/test-timezone.ts`, and the server tests open their own `bun:sqlite` space, so no test can reach shared data.
- **Git hooks are never skipped.** A Claude Code hook in `.claude/settings.json` blocks `--no-verify` and lefthook overrides. A failing hook gets its cause fixed; a flaky test is a bad test.
- **Run only the relevant tests locally.** CI runs the full suite.
- **Friction gets fixed or filed.** Development speed is a goal in itself. An agent that hits a manual step, a repeated prompt, a slow command, or a flaky tool fixes it in the same thread when the fix is small, and otherwise opens a GitHub issue with its findings and a proposed fix (as with [#84](https://github.com/smirea/a-better-me/issues/84), HealthKit on fresh simulators).
- **Environments start on the default path.** The common case is the owner using the app with everything allowed and real-looking data, so simulators get every permission granted (whenever the app's last launch left a prompt unanswered, which Debug simulator builds record in their defaults, `scripts/run` runs `UITests/App/PermissionsGrant`, which answers the app's launch-time Health sheet and system prompts until the app reports them all answered; a timeout on a quiet screen gave up before a slow launch on a busy Mac asked, so prompts came back) and Debug builds seed their data. `simctl privacy grant all` is not used: it also resets the app's Health access, which made the sheet return on every run. Testing a denied, limited, or empty state is the exception: the agent revokes the permission or clears the data for that test.
- **Apple Health is off in Debug simulator builds.** The one exception to the default path. Health's sheet kept stopping agents after the grant above: an existing simulator never reran it, and every new Health type asks again on every simulator. Most work never touches Health, and the seeded app weigh-ins and imported steps still fill the Dashboard. So `HealthStore.isAvailable` is false there, and the app takes the path it takes when Health is denied. An agent working on Health runs `scripts/run --health on`, which persists in the app's defaults and answers the sheet; `--health off` turns it off again. Release builds and Debug builds on a device always use Health, and the watch app is not gated.
- **One agent writes each feature end to end.** The thread that owns a feature writes all of its code, across iOS, the server, and shared types, instead of splitting it among worker threads. Split work drifted between clients, duplicated helpers, and clashed on names. Subagents only review and research, unless the owner asks for a coding delegate.
- **The task orchestrator works the owner's backlog.** The owner files A Better Me's bugs and features as tasks in ProcrastiMate's `a better me` project. `/task-orchestrator-start` (`.claude/skills/task-orchestrator-start/`) runs in the main checkout: it triages those tasks, bundles them into jobs by area, launches one worker per job with the committed `brief.md`, completes each task once its PR merges, and files followups back as tasks. Only the orchestrator talks to the task API (`scripts/pm`, with the AI account's token from the ProcrastiMate checkout), and keeps its session state in the git-ignored `.orchestrator/`. Jobs stay independent: no cap on how many run, no waiting on a sibling, and a worker that hits a conflict reads the history of what landed before resolving it. Workers report through one JSON result, upload a new setting's values after their merge ([Environment](environment.md)), and fix any playbook instruction they find stale in their own PR; `skill-references.test.ts` fails when the playbook names a path that is gone.
- **Simulators are named, claimed, gated, and collected.** `agent-simulator udid` creates the worktree's simulator, named after its directory, and claims it. `app-ios/scripts/run` claims the simulator it targets for its worktree (`agent-simulator claim`), and a headless boot waits, saying so, while the Mac's total CPU is above 70% or 4 iPhone simulators are booted (`agent-simulator wait`): the machine judges load instead of a cap on agents. Removing a worktree deletes its simulators with their paired watches, and `agent-simulator gc`, which `worktree-gc.ts` runs, shuts claimed simulators down after 15 idle minutes and deletes those whose worktree is gone and the DerivedData of removed checkouts.
- **Reference-app research is serialized.** Only one agent can drive a reference app's window at a time. Research runs before the feature work starts and lands as a spec with screenshots under `docs/research/`, which the implementing agent reads instead of driving the app.

## Worktree storage

- T3 generates a descriptive branch name concurrently with setup. Never pass a branch name to setup in a T3-owned worktree or rename its branch from a setup/teardown hook. Resource identity follows the worktree directory, not the branch name.
- On this Mac, `agent-t3-worktree settle` runs when a thread settles. Besides removing merged worktrees, it removes only wholly ignored Xcode `DerivedData` and `.build` directories in linked worktrees, independently of whole-worktree retention. It preserves source, uncommitted files, env files, and databases, and skips worktrees with running T3 turns or open build files. Main checkouts are never cleaned. The next build regenerates the output.
- Native launchers reuse `DerivedData/SourcePackages` within each checkout; device and simulator compilation outputs remain separate. Do not create ad hoc `check`/`test` package caches: pass `-clonedSourcePackagesDirPath app-ios/DerivedData/SourcePackages` when running `xcodebuild` from the repository root. Each worktree keeps its own package directory so parallel tasks do not mutate another checkout's dependencies.
- Branch metadata mismatches can still block T3's whole-worktree cleanup. Repair ownership through T3 rather than force-removing a potentially live checkout; build-cache cleanup does not depend on the saved branch name.
