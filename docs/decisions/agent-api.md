# Agent API

The owner's data is reachable over HTTP for automation, so an agent such as an AI coach can read training history and manage programs, templates, gyms, and settings without the app.

- **One entry point, the only open route.** `GET /api` without a token answers how to get one: create it in the iOS app under Dashboard gear > Settings > API Tokens and send it as `Authorization: Bearer abm_...`. With a token it answers everything an agent needs in one response: a Markdown guide to the domain and conventions, a snapshot of the current state (active program and its next day, default gym, the session in progress, counts), and the full OpenAPI 3.1 document. `GET /api/openapi.json` serves the same document for tools that import specs, behind a token. Every other path answers a bare 401 (`{ ok: false, error }`) without a token, and every path outside `/api` answers 404. There is no health route.
- **Resources.** Exercises (the bundled catalog plus custom ones, with search, a gym filter, per-exercise settings, and a per-exercise history of logged sets for progression), equipment, templates, sessions, programs (with inline template creation, activation, and the next day), gyms (with the default), settings (with the Nutrition settings), body weights, and the [Nutrition](nutrition.md) tables: foods, recipes, food entries, favorites, food log notes, nutrition days, body metrics, nutrition plans, and nutrient goals. Templates and sessions keep the stored block tree as is, so the API and the app share one shape.
- **Routes are one registry.** `server/src/agent/routes.ts` lists each operation with its Zod query, body, and response schemas; the nutrition operations live in `nutrition.ts` beside it and join the same list. The router dispatches from the registry, and the OpenAPI document is generated from it (`openapi.ts`), so the docs cannot drift from the code. Schemas with a `meta` id become shared components; a request component that differs from its response twin gets an `Input` suffix.
- **Writes go through the sync engine.** The API runs where the space lives: in the Bun process locally, inside the `Space` Durable Object in production. It reads the tables directly and writes through `space.sync` as the client `agent-api`, so each write gets the same validators, change log, and tombstones as a phone's, and devices are nudged over `/api/live` to pull at once. The engine checks each write on its own, so the request schemas enforce everything first: the Swift decoders are strict about the block tree, program days, and custom exercises, and a tree the phone cannot decode would hide the whole row. Unknown exercise, equipment, template, gym, and program references are refused with 422.
- **Bot tokens sync as hashes.** `api_tokens` is a synced table of `{ name, token_hash, hint, created_at }`. The phone makes a random `abm_` token, shows it once, and stores only its SHA-256, so neither the server nor the backups hold a usable token. A token works once the phone has synced and stops after the delete that revokes it syncs. The server looks tokens up by hash; the owner token is accepted too. Bot tokens reach only the agent API, never `/api/sync` or `/api/live`, and the API exposes no route to the tokens table, so an agent cannot mint or revoke tokens.
- **The catalog comes from the iOS bundle.** The server imports `app-ios/Sources/App/Resources/Catalog/exercises.json` and `equipment.json` instead of holding a copy, which adds about 400 KB gzipped to the Worker.
- **Mirrors of app behavior.** Activating a program starts a fresh run at cycle 1 and deactivates the others, as `LocalStore.activate` does. The first gym becomes the default. Deleting a program deletes its templates. A session created from a template copies its blocks, with the cycle's targets when it names a program position. Logging a program session does not advance the cycle; an agent sets `currentCycle` itself.
- **Weights are kilograms on the wire,** whatever `settings.weightUnit` displays.
- **The food database.** `GET /food-database/barcode/{barcode}` and `GET /food-database/search?q=` proxy Open Food Facts as the app's `Food` shape, with nutrients under registry ids ([Nutrition](nutrition.md#food-data)). The app's own food search calls them with the owner token; route handlers may be async for this.
- **Nutrition follows the app's rules.** Entries, favorites, and recipe ingredients store a food snapshot and a serving; a write gives the snapshot, or a `foodId` or `recipeId` the server snapshots. Responses add what the app derives: an entry's `amounts` (the one scaling rule), a recipe's per-serving `nutrition`, and a day's `totals` (`GET /food-log/{day}`). Energy is kcal, tape measurements centimeters, and days `YYYY-MM-DD`. The app's caps hold here too: five notes a day (409), and a 51st favorite evicts the oldest.
- **Day-keyed rows are PUT.** Nutrition days, body metrics, plans, and nutrient goals have ids built from their key (`<day>`, `<day>/<kind>`, `<day>/<nutrient>`), so `PUT` sets the value for the key and a second write replaces it, as `LocalStore.put` does.
- **Creates take an id.** Foods, recipes, entries, favorites, notes, and weigh-ins accept an optional `id` (a UUID, or `usda-<fdcId>` and `off-<barcode>` for cached foods), and a create whose id exists answers 409. An importer derives ids from its source rows, so running it again converges instead of duplicating ([Nutrition](nutrition.md), Import).
