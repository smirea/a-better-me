# Sync

The app works fully offline and syncs with the server whenever it has connectivity. The design copies procrastimate's (`~/code/procrastimate/docs/decisions/sync.md`): Postgres holds the truth, PowerSync streams it into a SQLite database on each device, and the device's writes go up through one server route. Only features that need the network to function, such as an AI recipe parser, may need a connection. Nothing in Workouts does.

## Shape

- **The device's database is the app's database.** Every screen reads and writes a local SQLite file that PowerSync manages. A write lands locally at once and joins PowerSync's upload queue. Nothing waits on the network, and there is no conflict screen.
- **One owner, no accounts.** A Better Me has one user ([Product goals](product.md)), so there is no sign-up, session, or `user_id` column. One secret, `OWNER_TOKEN`, authorizes a device. The app stores it in the Keychain once, from Settings, and sends it as a bearer. procrastimate's Better Auth, sharing, `access` rows, and guest checks have nothing to protect here, so they are left out.
- **Synced tables.** `workout_templates`, `workout_sessions`, `custom_exercises`, `exercise_settings`, and `settings`. Ids are client-made, so rows created offline never collide. `exercise_settings` is keyed by the exercise ID, and `settings` is one row with the id `settings`, so two devices editing either offline converge on one row instead of creating duplicates. Device-local state, such as the Keychain token and the simulator launch harness, never syncs.
- **Columns hold what the model holds.** A template's and a session's ordered block tree stays one JSON column (`blocks`), as in the SwiftData model. Postgres gets `jsonb`, and PowerSync and the device get JSON text.

## Server

- **Postgres on Supabase, in procrastimate's projects.** The Supabase organization is on the free plan, whose two projects procrastimate already uses. So A Better Me has its own database, `a_better_me`, inside each of them: `procrastimate-dev` for `dev` and `procrastimate-prod` for `prod`. The database is owned by its own login role, `a_better_me_app`, and replicated by `a_better_me_powersync`. Neither role can connect to procrastimate's `postgres` database. Supabase's dashboard and backups cover only `postgres`, so the Worker's daily cron dumps `a_better_me` to R2, as procrastimate's does. Moving to dedicated projects is a dump and restore, once the organization is on a paid plan.
- **The Cloudflare Worker serves the API.** It runs at `https://a-better-me.stf.lol` on the same account and `stf.lol` zone as procrastimate, pinned to `aws:us-east-1` beside the database. It reaches Postgres through Hyperdrive config `a-better-me-prod` (`7d04f2790d4d4dc799760630c557cc32`, caching off). The Bun dev server runs the same handler with `DATABASE_URL`. CI deploys every push to `master`.
- **Routes.** `GET /api/sync/token` takes the owner bearer and answers `{ token, endpoint }`: an hour-long EdDSA JWT that the server signs with `POWERSYNC_JWT_PRIVATE_KEY`, with `sub: "owner"` and `aud: "powersync"`. `POST /api/upload` takes `{ writes: [{ op, table, id, values, opId }] }` from PowerSync's queue and applies each write as one idempotent single-row statement: a put upserts, a patch updates only the sent columns, and a delete removes the row. One bad write is rejected alone and the batch still answers 200, because PowerSync stops uploading on a 4xx. `/api/powersync/*` forwards to `POWERSYNC_URL`, so a device talks to one origin. Without `POWERSYNC_URL`, the token route answers 503 and the app stays local.
- **Conflicts.** A write carries only the columns it changed, and the last write to reach the server wins per column. A delete beats a later edit. A template edited on two devices offline keeps the later `blocks` whole, because the tree is one column. With one person on one phone, that is the right trade for keeping the model as it is.
- **Migrations** are drizzle-kit's, append-only, and bundled into the Worker, which applies the missing ones on its first request. The `powersync` publication names exactly the synced tables, and a migration grants `a_better_me_powersync` read access to them.

## PowerSync

- **Locally, one Docker PowerSync per worktree.** It runs next to a shared Docker Postgres, as procrastimate's dev hosting does, and trusts the committed `powersync/local/INSECURE-dev-jwt-key.json`. `bun scripts/setup-worktree.ts` provisions both. A sync smoke script proves the loop: token, upload, and the row streaming back.
- **PowerSync Cloud for production is not provisioned yet.** The PowerSync organization is on the free plan, whose two instances procrastimate uses, and creating a third fails with `PLAN_LIMIT_REACHED`. The prod config is ready in `powersync/prod/`, and its public token key is `token-public-key.json`. Until the owner upgrades the PowerSync organization (or picks another host), production runs the Worker and database with sync off, and the app keeps its data locally.

## iOS

- **PowerSync with GRDB replaces SwiftData.** Records over PowerSync's views are how every read and write reaches the local database, through `powersync-swift`, pinned exactly, with its `PowerSyncGRDB` product. Screens observe the database with GRDB's `ValueObservation`. This matches procrastimate's iOS app, which dropped SwiftData for the same reason: the model is value trees, and SwiftData adds a mapping layer and migrations the product doesn't want.
- **The connector** gets a token from `/api/sync/token` with the Keychain bearer, uploads queue batches to `/api/upload`, and retries on network failure. It connects while a token is stored. A launch never waits on the network, and the first frame reads the local file.
