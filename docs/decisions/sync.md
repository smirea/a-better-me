# Sync

The app works fully offline and syncs with the server whenever it has connectivity. The design copies procrastimate's (`~/code/procrastimate/docs/decisions/sync.md`): Postgres holds the truth, PowerSync streams it into a SQLite database on each device, and the device's writes go up through one server route. Only features that need the network to function, such as an AI recipe parser, may need a connection. Nothing in Workouts does.

## Shape

- **The device's database is the app's database.** Every screen reads and writes a local SQLite file that PowerSync manages. A write lands locally at once and joins PowerSync's upload queue. Nothing waits on the network, and there is no conflict screen.
- **One owner, no accounts.** A Better Me has one user ([Product goals](product.md)), so there is no sign-up, session, or `user_id` column. One secret, `OWNER_TOKEN`, authorizes a device. The app stores it in the Keychain once, from Settings, and sends it as a bearer. procrastimate's Better Auth, sharing, `access` rows, and guest checks have nothing to protect here, so they are left out.
- **Synced tables.** `workout_templates`, `workout_sessions`, `custom_exercises`, `exercise_settings`, `settings`, `programs`, `gym_profiles`, and `body_weights`. Ids are client-made, so rows created offline never collide. `exercise_settings` is keyed by the exercise ID, and `settings` is one row with the id `settings`, so two devices editing either offline converge on one row instead of creating duplicates. Device-local state, such as the Keychain token and the simulator launch harness, never syncs.
- **Columns hold what the model holds.** `shared/db/schema.ts` defines the tables and `SYNCED_TABLES`. A template's and a session's ordered block tree stays one JSON column (`blocks`), as in the SwiftData model, and a custom exercise is its whole `Exercise` in one `exercise` column. `settings` holds `weight_unit` (`kg` or `lb`) and one rest default per `RestCategory` (`rest_compound_upper` 120, `rest_compound_lower` 180, `rest_upper_isolation` 90, `rest_lower_isolation` 90, `rest_core` 60). Milestone 2 added `programs` (`config` and `days` as JSON, `cycles`, `current_cycle`, `active`, `archived`), `gym_profiles` (`equipment` as JSON, `is_default`), `body_weights` (`measured_at`, `weight_kg` as double precision, `source`), `program_id`, `gym_id`, and `archived` on templates, `program_id`, `program_day_id`, `cycle`, `gym_id`, and `paused_seconds` on sessions, `do_not_recommend` and `overrides` on `exercise_settings`, and the JSON columns `workout`, `profile`, `dashboard`, and `shortcuts` on `settings`. Every nested setting is a JSON object the app rewrites whole per column, so a new setting needs no migration, and every new column has a default or is nullable, so a put that omits it is valid. Check constraints refuse what the model can't hold: a `blocks` or `days` that is not an array, a `config`, `equipment`, `overrides`, or settings JSON that is not an object, a custom exercise id without `custom-`, an unknown weight unit or body weight source, a negative rest, cycle, pause, or body weight, and a session that names a program without its day and cycle. A check never relates two columns that two devices can patch separately, such as `cycles` and `current_cycle`; the reader clamps. Nothing enforces one active program or one default gym on the server, because a unique index would reject a whole coalesced patch when two devices flip the flag offline; `LocalStore.activateProgram` and `setDefaultGym` keep it locally and the reader takes the most recently updated row. The inner shape of every JSON column is the app's to validate.
- **One wire shape, both directions.** What PowerSync streams down is what the device uploads. Timestamps are `timestamptz` in Postgres and ISO 8601 UTC text with milliseconds on the wire (`2026-10-23T22:37:52.264Z`): the sync config sets `timestamp_max_precision: milliseconds`, so a value round-trips byte for byte instead of coming back with Postgres's microseconds. `jsonb` travels as JSON text, booleans as 0 or 1, and integers as numbers. Upload accepts JSON as text or as a value, and integers and booleans as numeric strings too.

## Server

- **Postgres on Supabase, in procrastimate's projects.** The Supabase organization is on the free plan, whose two projects procrastimate already uses. So A Better Me has its own database, `a_better_me`, inside each of them: `procrastimate-dev` for `dev` and `procrastimate-prod` for `prod`. The database is owned by its own login role, `a_better_me_app`, and replicated by `a_better_me_powersync`. Neither role can connect to procrastimate's `postgres` database. Supabase's dashboard and backups cover only `postgres`, so the Worker's daily cron dumps `a_better_me` to R2, as procrastimate's does. Moving to dedicated projects is a dump and restore, once the organization is on a paid plan.
- **The Cloudflare Worker serves the API.** It runs at `https://a-better-me.stf.lol` on the same account and `stf.lol` zone as procrastimate, pinned to `aws:us-east-1` beside the database. It reaches Postgres through Hyperdrive config `a-better-me-prod` (`7d04f2790d4d4dc799760630c557cc32`, caching off). The Bun dev server runs the same handler with `DATABASE_URL`. CI deploys every push to `master`. See [Hosting](hosting.md).
- **Routes.** One fetch handler, `server/src/api.ts`, which Bun serves locally and the Worker in production. `GET /status` is open. `GET /api/sync/token` takes the owner bearer and answers `{ token, endpoint }`: an hour-long EdDSA JWT that the server signs with `POWERSYNC_JWT_PRIVATE_KEY`, with `sub: "owner"` and `aud: "powersync"`, and `endpoint`, the server's own `/api/powersync`. `POST /api/upload` takes `{ writes: [{ op, table, id, values, opId }] }` from PowerSync's queue and answers `{ rejected: [{ table, id, reason }] }`. `/api/powersync/*` forwards to `POWERSYNC_URL`, so a device talks to one origin; PowerSync checks its own `Token` there. Without `POWERSYNC_URL`, the token route and the proxy answer 503 and the app stays local. A missing or wrong bearer answers 401, and an error answers `{ ok: false, error }`.
- **Upload rules.** Each write is one single-row statement, run in order, with no transaction, so every write converges when PowerSync resends a batch. A put upserts the whole row: a column it leaves out, which is how PowerSync sends a null, gets its default or null, and a required column must be there. A patch sets only the columns it names, and patching a row that is gone changes nothing. A delete removes the row. A write with an unknown table, op, or column type, a missing required column, a null for a required column in a patch, U+0000 anywhere, a `settings` id other than `settings`, or a `settings` delete is rejected alone with a reason; so is any write the database refuses with a data or constraint error. The batch still answers 200, because PowerSync stops uploading on a 4xx. Columns the server doesn't know are ignored, so an app a version ahead still uploads. Only a body that isn't `{ writes: [...] }` answers 400, and only a server failure answers 500, which PowerSync retries. `opId` is accepted and unused: there is no write log.
- **Conflicts.** A write carries only the columns it changed, and the last write to reach the server wins per column. A delete beats a later edit. A template edited on two devices offline keeps the later `blocks` whole, because the tree is one column. With one person on one phone, that is the right trade for keeping the model as it is.
- **Migrations** are drizzle-kit's, append-only, in `server/drizzle/`. `bun run db:generate` writes the next one and bundles all of them into `server/src/db/migrations.generated.ts`, since the Worker cannot read files; CI fails when either is stale. The Worker applies the missing ones once per isolate, on its first request, and the Bun server at startup, under one advisory lock. The custom migration `0001_powersync` creates the `powersync` publication with exactly the synced tables and grants `a_better_me_powersync` read access to them where that role exists (Supabase, not local Docker). A migration that adds a synced table appends its `ALTER PUBLICATION powersync ADD TABLE` and grant to the generated file, as `0002` does, so one migration carries the table and its replication. `shared/db/schema.test.ts` fails when `powersync/sync-config.yaml` streams a different set of tables than `SYNCED_TABLES`.
- **The owner token locally** is `insecure-local-dev-owner-token` (`DEV_OWNER_TOKEN` in `server/src/config.ts`), and the signing key is `powersync/local/INSECURE-dev-jwt-key.json`. Production refuses to start without its own `OWNER_TOKEN` and `POWERSYNC_JWT_PRIVATE_KEY`, and refuses the development token.
- **The web client's proxy strips `/api`.** Vite rewrites a browser's `/api/status` to the server's `/status`, so the sync routes, which keep their `/api` prefix to match production, need that rewrite changed before the web client syncs. Only the iOS app syncs today, and it calls the API directly.

## PowerSync

- **One sync config.** `powersync/sync-config.yaml` streams every synced table whole to any token PowerSync accepts, since there is one owner and no `user_id`. Local Docker and production share it.
- **Locally, one Docker PowerSync per checkout.** `docker/compose.yaml` runs one Postgres 17 container (`a-better-me-postgres`, `wal_level=logical`) on port 6159, inside A Better Me's 6150 slot, shared by every checkout, each in its own database: `wt_<worktree directory>` for a worktree, `main` for the main checkout, each beside a `_powersync` storage database. Each checkout has its own PowerSync container (`a-better-me-powersync-<checkout>`, labelled `a-better-me.checkout`) on its base port + 2, trusting the committed `powersync/local/INSECURE-dev-jwt-key.json`. Every name differs from procrastimate's containers on the same Mac. `bun scripts/setup-worktree.ts` starts it for a worktree and writes `DATABASE_URL` and `POWERSYNC_URL` into `.env.override`; `bun scripts/teardown-worktree.ts` removes the container and drops the databases with their replication slot. The main checkout runs `bun run stack` (`up`, `down`, `--reset-db`), which writes the same two settings into its `.env.override`.
- **The sync smoke proves the loop.** `bun run sync:smoke [--api URL]` against a running server gets a token, opens the stream through the proxy, uploads a put, a patch, and a delete of a template and sees each stream back, sees a bad write rejected alone, and sees a boolean come back as 1. `bun scripts/wrangler-dev.ts` runs the Worker build on the local stack on the base port + 3, so the same smoke covers it.
- **PowerSync Cloud for production is not provisioned yet.** The PowerSync organization is on the free plan, whose two instances procrastimate uses, and creating a third fails with `PLAN_LIMIT_REACHED`. The prod config is ready in `powersync/prod/service.yaml`: it replicates `a_better_me` as `a_better_me_powersync` and trusts `token-public-key.json`, which `bun scripts/secrets.ts public-key` derives from the prod signing key. Until the owner upgrades the PowerSync organization (or picks another host), production runs the Worker and database with sync off (`POWERSYNC_URL` is empty in `wrangler.jsonc`), uploads still land in Postgres, and the app keeps its data locally. Turning sync on is deploying that config and setting the var.

## iOS

- **The sync engine's Swift package replaces PowerSync.** `https://github.com/smirea/sync-engine` on branch `master` is the app's one dependency and brings GRDB; the app links its `SyncEngine` and `GRDB` products. Each model is a plain struct that is also a GRDB record over its table (`SyncedRecord`): `WorkoutTemplate`, `WorkoutSession`, `CustomExercise`, `ExerciseSettings`, `AppSettings`, `Program`, `GymProfile`, and `BodyWeight`. The value types inside (`WorkoutBlock`, `WorkoutSet`, `Exercise`) are unchanged.
- **The client schema is a generated file.** `Sync/Generated/SyncSchema.swift` holds `syncSchema`: each table's columns besides `id`, and the complete client DDL in the order the engine's `docs/protocol.md` states (the eight tables, one `ALTER TABLE ... ADD COLUMN` per column so a grown schema migrates additively, `_outbox`, `_meta`, the capture triggers). The engine's generator emits it from the server's Drizzle schema; until that generator lands, the file is written by hand to the same text and is the only place the app names a column type.
- **Column shapes.** Ids are text: a lowercase UUID for workouts and sessions, the exercise id for the rest. Instants are ISO 8601 in UTC with milliseconds (`Instant`), which the JSON trees also use for `completedAt`, so an export reads without the app. JSON columns are compact text with sorted keys (`RowJSON`), so the same value always encodes the same way and a re-save of an unchanged tree fires no update trigger. A boolean is an INTEGER 0 or 1. A double (`weight_kg`) is a REAL column. The engine never interprets a value, so what one device writes is what every other device reads, byte for byte. A settings-like JSON column (`settings.workout`, `profile`, `dashboard`, `shortcuts`, `exercise_settings.overrides`, `programs.config`, `gym_profiles.equipment`) decodes through `Row.json(_:over:)`: the stored object is deep-merged over the encoded Swift default and decoded with synthesized `Codable`, so a missing key reads its default, and a column that still fails to decode reads as the default and logs instead of failing the observation. Data columns (`blocks`, `days`, `exercise`) stay strict. A new column arrives NULL on devices for rows written before it, so every new column reads NULL-safely, and a field added inside the block tree is Optional, because synthesized `Decodable` has no defaults.
- **One store, one writer.** `LocalStore` opens the database (`Application Support/a-better-me/a-better-me.sqlite`) and runs the engine's `migrate()` in its initializer, before the first screen, so there is no loading state. Every write goes through `store.write`, `insert`, `modify`, `editTemplate`, `updateSettings`, or `delete`, which chain one after another in the order they were called, each in one transaction, so a view never races its own earlier edit. `modify` reads the row, applies the change, and writes only the columns that differ (`updateChanges`); the engine's `AFTER UPDATE OF` triggers record those columns, and the next sync sends them as one patch.
- **The first launch after the switch imports the old layout once.** Before the engine, the device's file held each table as a view over `ps_data__<table>` (`id`, `data` as JSON), and the phone holds the only copy of the owner's data, since the server never had a row. `LegacyImport` drops those views (a `CREATE TABLE IF NOT EXISTS` would otherwise keep the view and the triggers could not be created), runs `migrate()`, copies every `ps_data__` row into its table with `json_extract`, filling a missing key with the column's default, and drops every `ps_` table. The copy runs with the capture triggers live, so each row lands in `_outbox` as an insert and the first sync puts everything on the server. A database without `ps_data__` tables passes through unchanged, so the step is idempotent. The old upload queue needs no handling, because `ps_data__` already held the local state.
- **Screens observe the database.** `@Observe(WorkoutTemplate.all)`, `@Observe(WorkoutSession.inProgress)`, `@Observe(AppSettings.current)`, and the other `DatabaseQuery` values replace SwiftData's `@Query`: a GRDB `ValueObservation` read synchronously for the first frame and again after any local write or applied sync that touches the tables it reads. Sorting happens in Swift, on the parsed instants. Editors keep a local copy of the blocks they edit and write each change through; a change from another device replaces the copy only while none of this device's writes is still in flight, and otherwise the later write wins, as on the server.
- **Settings live in the synced row.** The weight unit and the rest defaults, which `@AppStorage` held, are the `settings` row with the id `settings`. A device creates the row whole the first time it changes a setting, with the schema defaults in every column it did not touch (`AppSettings.encode` writes a rest default for an unset category, because the columns are `NOT NULL`), and patches it ever after. Two devices that both create it offline would reset each other's other columns to the defaults once, because the server's put replaces the whole row; with one person on one phone that is acceptable. The Levels period stays in `@AppStorage`, because it is view state, not data.
- **The client owns the loop.** `SyncClient` watches `_outbox` and syncs 100 ms after a local write, on launch, on foreground, when the network comes back, on a `head` message from the `/api/live` WebSocket, and every minute. One `POST /api/sync` carries the coalesced outbox with the Keychain owner token as a bearer and brings back the rows changed since the cursor. The Sync screen under More maps the client's status: idle is connected, syncing is syncing, a URL error is offline, a 401 is "Invalid token", and any other failure is "Sync failed" with its reason; all but the 401 retry with backoff capped at a minute. Saving a token calls `sync()`, the one call that tries a refused token again; forgetting it stops the client. A rejected write is dropped by the server, so the screen lists the client's last rejections. The Debug launch argument `-syncToken <token>` stores a token for simulators.
- **The Keychain needs an entitlement.** `Config/App.entitlements` names the app's keychain access group, and the launcher signs simulator builds ad hoc (`CODE_SIGN_IDENTITY=-`) so the entitlement is embedded; an unsigned build fails every Keychain call with `errSecMissingEntitlement`. CI's compile check still runs with signing off.
