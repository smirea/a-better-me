# Sync

The app works fully offline and syncs with the server whenever it has connectivity. The server runs our own sync engine, `https://github.com/smirea/sync-engine`, whose `docs/protocol.md` is the contract: one SQLite space on the server holds the truth, every device holds the same tables in its own SQLite file, and one request carries a device's writes up and the changed rows down. Only features that need the network to function, such as an AI recipe parser, may need a connection. Nothing in Workouts does.

## Shape

- **The device's database is the app's database.** Every screen reads and writes a local SQLite file. A write lands locally at once, and the engine's triggers queue it in `_outbox` for the next sync. Nothing waits on the network, and there is no conflict screen.
- **One owner, no accounts.** A Better Me has one user ([Product goals](product.md)), so there is no sign-up, session, or `user_id` column. One secret, `OWNER_TOKEN`, authorizes a device. The app bundles it at build time and sends it as a bearer, so there is nothing to set up on the phone ([iOS](#ios)). procrastimate's Better Auth, sharing, `access` rows, and guest checks have nothing to protect here, so they are left out.
- **Synced tables.** `workout_templates`, `workout_sessions`, `custom_exercises`, `exercise_settings`, `settings`, `programs`, `gym_profiles`, `body_weights`, `api_tokens` ([Agent API](agent-api.md)), and Nutrition's `foods`, `recipes`, `food_entries`, `food_favorites`, `nutrition_days`, `body_metrics`, `nutrition_plans`, and `nutrient_goals` ([Nutrition](nutrition.md)). Ids are client-made, so rows created offline never collide. `exercise_settings` is keyed by the exercise ID, `settings` is one row with the id `settings`, and the nutrition rows that hold one value per key (a day, a day and metric, a day and nutrient, a cached food) are keyed by it, so two devices editing one offline converge on one row instead of creating duplicates. Device-local state, such as the simulator launch harness, never syncs.
- **One schema, both sides.** `shared/db/schema.ts` defines the tables as Drizzle `sqlite-core` tables, `SYNCED_TABLES`, and `schema`, the engine's `defineSchema({ tables, values })`. The server's space and every device run the DDL the engine derives from it, so a column exists on both sides or on neither. Columns use SQLite's storage classes: an instant is ISO 8601 UTC text with milliseconds, JSON is text, a boolean is an INTEGER 0 or 1, and `weight_kg` is REAL. A template's and a session's ordered block tree stays one JSON column (`blocks`), and a custom exercise is its whole `Exercise` in one `exercise` column. `settings` holds `weight_unit` (`kg` or `lb`), one rest default per `RestCategory` (`rest_compound_upper` 120, `rest_compound_lower` 180, `rest_upper_isolation` 90, `rest_lower_isolation` 90, `rest_core` 60), and the JSON objects `workout`, `profile`, `dashboard`, `shortcuts`, and `nutrition`, each rewritten whole by the app, so a new setting needs no migration. Every column has a default or is nullable, so a put that omits it is valid, and the engine can add it to an existing table.
- **Validators replace the check constraints.** `values` in `defineSchema` carries a Zod schema per column the engine checks before a write lands: `weight_unit` and `source` are their enums, `blocks` and `days` are arrays, `exercise`, `config`, `equipment`, `overrides`, and the settings objects are objects, rest seconds and `paused_seconds` are non-negative integers, `cycle`, `cycles`, and `current_cycle` are at least 1, and `weight_kg` is positive. A check that related two columns, a session's program with its day and cycle, is gone: two devices can patch them separately, so the reader tolerates a half-set trio, as it already clamps `current_cycle` to `cycles`. The engine validates columns, never the id, so the `custom-` prefix and the `settings` id are the app's to keep. Nothing enforces one active program or one default gym on the server, because a unique index would reject a whole coalesced patch when two devices flip the flag offline; `LocalStore.activateProgram` and `setDefaultGym` keep it locally and the reader takes the most recently updated row. The inner shape of the workout JSON columns is the app's to validate; the nutrition data columns' inner shapes are validated here too ([Nutrition](nutrition.md#rules)). A calendar day is `YYYY-MM-DD` text, checked by its own validator.
- **The wire carries values, uninterpreted.** A value is a JSON string, number, or null, stored as the column's storage class. The engine never parses an instant or re-encodes a JSON column, so what one device writes is what every other device and the backup read, byte for byte.

## Server

- **The engine serves two routes behind the owner token.** `POST /api/sync` takes `{ protocol: 2, client, cursor, writes, after }` and answers `{ head, acked, rejected, snapshot, rows, next }`: the device's coalesced outbox goes up, and every row changed since the cursor comes down. A cursor of 0, or one below the horizon that compaction moves up past old tombstones, gets a snapshot in pages: each page's `next` is the `after` of the following request, and `next` is null on the last page. `GET /api/live` is a WebSocket that sends `{ head }` to every device after any sync that advanced the head, so a device pulls at once instead of polling. `server/src/api.ts` is the one fetch handler both hosts run: `GET /status` is open, the two sync routes check the bearer with a constant-time compare, every other `/api` route is the [agent API](agent-api.md), and anything else is 404. The handler hands an authorized request to the host's engine: the Worker forwards it to the `Space` Durable Object with the `/api` prefix stripped, and the Bun server runs a space in-process.
- **One space, one Durable Object.** Production state is the SQLite storage of one Durable Object, `Space` in `server/src/worker.ts`, the engine's `SpaceObject` with this schema, reached as the space `owner`. The object serializes every write, so there are no locks and no connection pool, and it is created on first use, so a new environment needs no provisioning. See [Hosting](hosting.md) for its binding, recovery, and backups.
- **Write rules are the engine's.** A batch applies in one transaction in `seq` order, each write exactly once per client, so a resent batch changes nothing. A put upserts the whole row and fills a left-out column with its default; a patch sets only the columns it names and is a no-op on a missing row; a delete removes the row and leaves a tombstone, so devices that still hold the row drop it. A write that names an unknown table, a column of the wrong storage class, a null for a `NOT NULL` column, or a value a validator refuses is rejected alone with a reason, the batch still answers 200, and the response carries the server's current row for it, so the device replaces what the server refused. Columns the server doesn't know are ignored, so an app a version ahead still syncs. Only a body of the wrong shape answers 400, and a protocol other than 1 or 2 answers 426.
- **Conflicts.** The last write to reach the server wins per column. A delete beats a later patch. A template edited on two devices offline keeps the later `blocks` whole, because the tree is one column. With one person on one phone, that is the right trade for keeping the model as it is.
- **Schema changes are additive.** On start, the space and every device compare `PRAGMA table_info` with the schema and add the missing tables and columns; a removed column stays and is ignored, and a column whose type must change gets a new name. There are no migration files. `bun run generate` writes the device's copy of the schema, `app-ios/Sources/App/Sync/Generated/SyncSchema.swift`, which is committed because Xcode and CI build the app without running Bun first; `shared/db/schema.test.ts` fails when the committed file differs from the generator's output.
- **Paging and compaction settings are development only.** `SYNC_PAGE_SIZE`, `SYNC_RETENTION_MS`, and `SYNC_COMPACT_EVERY_MS` set the engine's page size, tombstone retention, and compaction interval, so a local server can show paging and compaction with a few rows. Production refuses to start with any of them set and keeps the engine defaults: 30 days of retention, hourly compaction, and 1000 rows per page.
- **The owner token locally** is `insecure-local-dev-owner-token` (`DEV_OWNER_TOKEN` in `server/src/config.ts`). Production refuses to start without its own `OWNER_TOKEN`, and refuses the development token.
- **Local servers need no services.** `bun run start:server` runs the handler with Bun over `.data/<checkout directory>.sqlite`, git-ignored, so the main checkout and every worktree keep their own data. `bun scripts/wrangler-dev.ts` runs the Worker build on the checkout's base port + 2 with its Durable Object state under `.wrangler/`, so the same `curl` round trip against `/api/sync` covers the production path. `server/src/api.test.ts` drives the same `handle` over an in-memory space.
- **Postgres, PowerSync, and the local Docker stack are retired.** The server never held a row before the engine, the phone holds the only copy of the owner's data, and the first sync after the switch puts it on the server ([iOS](#ios)). The `a_better_me` databases in Supabase's `procrastimate-dev` and `procrastimate-prod` projects, their `a_better_me_app` and `a_better_me_powersync` roles, the Hyperdrive config `a-better-me-prod`, and the PowerSync configs can be deleted after cutover.
- **The web client's proxy strips `/api`.** Vite rewrites a browser's `/api/status` to the server's `/status`, so the sync routes, which keep their `/api` prefix to match production, need that rewrite changed before the web client syncs. Only the iOS app syncs today, and it calls the API directly.

## iOS

- **The sync engine's Swift package replaces PowerSync.** `https://github.com/smirea/sync-engine` on branch `master` is the app's one dependency and brings GRDB; the app links its `SyncEngine` and `GRDB` products. Each model is a plain struct that is also a GRDB record over its table (`SyncedRecord`): `WorkoutTemplate`, `WorkoutSession`, `CustomExercise`, `ExerciseSettings`, `AppSettings`, `Program`, `GymProfile`, `BodyWeight`, `ApiToken`, and the Nutrition records (`Food`, `Recipe`, `FoodEntry`, `FoodFavorite`, `NutritionDay`, `BodyMetric`, `NutritionPlan`, `NutrientGoal`). The value types inside (`WorkoutBlock`, `WorkoutSet`, `Exercise`) are unchanged.
- **The client schema is a generated file.** `Sync/Generated/SyncSchema.swift` holds `syncSchema`: each table's columns besides `id`, and the complete client DDL in the order the engine's `docs/protocol.md` states (the tables, one `ALTER TABLE ... ADD COLUMN` per column so a grown schema migrates additively, `_outbox`, `_meta`, the capture triggers). The engine's generator emits it from the server's Drizzle schema; until that generator lands, the file is written by hand to the same text and is the only place the app names a column type.
- **Column shapes.** Ids are text: a lowercase UUID for workouts and sessions, the exercise id for the rest. Instants are ISO 8601 in UTC with milliseconds (`Instant`), which the JSON trees also use for `completedAt`, so an export reads without the app. JSON columns are compact text with sorted keys (`RowJSON`), so the same value always encodes the same way and a re-save of an unchanged tree fires no update trigger. A boolean is an INTEGER 0 or 1. A double (`weight_kg`) is a REAL column. The engine never interprets a value, so what one device writes is what every other device reads, byte for byte. A settings-like JSON column (`settings.workout`, `profile`, `dashboard`, `shortcuts`, `nutrition`, `exercise_settings.overrides`, `programs.config`, `gym_profiles.equipment`) decodes through `Row.json(_:over:)`: the stored object is deep-merged over the encoded Swift default and decoded with synthesized `Codable`, so a missing key reads its default, and a column that still fails to decode reads as the default and logs instead of failing the observation. Data columns (`blocks`, `days`, `exercise`, and the nutrition snapshots, servings, and plans) stay strict. A new column arrives NULL on devices for rows written before it, so every new column reads NULL-safely, and a field added inside the block tree is Optional, because synthesized `Decodable` has no defaults.
- **One store, one writer.** `LocalStore` opens the database (`Application Support/a-better-me/a-better-me.sqlite`) and runs the engine's `migrate()` in its initializer, before the first screen, so there is no loading state. Every write goes through `store.write`, `insert`, `put`, `modify`, `editTemplate`, `updateSettings`, `delete`, or the Nutrition writes built on them, which chain one after another in the order they were called, each in one transaction, so a view never races its own earlier edit. `modify` reads the row, applies the change, and writes only the columns that differ (`updateChanges`); the engine's `AFTER UPDATE OF` triggers record those columns, and the next sync sends them as one patch.
- **The first launch after the switch imports the old layout once.** Before the engine, the device's file held each table as a view over `ps_data__<table>` (`id`, `data` as JSON), and the phone holds the only copy of the owner's data, since the server never had a row. `LegacyImport` first writes a consistent copy of the whole file with `VACUUM INTO` to `a-better-me.before-sync-engine.sqlite` beside the database, when `ps_data__` tables exist and the copy does not. Then it drops the views (a `CREATE TABLE IF NOT EXISTS` would otherwise keep the view and the triggers could not be created), runs `migrate()`, copies every `ps_data__` row into its table with `json_extract`, filling a missing key with the column's default, drops the other `ps_` tables (`ps_crud`, `ps_buckets`, `ps_oplog`, and the rest), and writes `_meta.legacy_import` with the time. The copy runs with the capture triggers live, so each row lands in `_outbox` as an insert and the first sync puts everything on the server. Every later launch sees the `_meta` key and only migrates. The old upload queue needs no handling, because `ps_data__` already held the local state.
- **The old rows stay until the server is known to hold them.** A legacy row the server's validators refuse comes back as a tombstone and the client deletes it locally, so an import that dropped `ps_data__` would leave such a row nowhere. The `ps_data__` tables and the backup file are the owner's copy: the app never reads or deletes either. A later release may drop the `ps_data__` tables and the backup, after the owner confirms the server holds everything.
- **Screens observe the database.** `@Observe(WorkoutTemplate.all)`, `@Observe(WorkoutSession.inProgress)`, `@Observe(AppSettings.current)`, and the other `DatabaseQuery` values replace SwiftData's `@Query`: a GRDB `ValueObservation` read synchronously for the first frame and again after any local write or applied sync that touches the tables it reads. Sorting happens in Swift, on the parsed instants. Editors keep a local copy of the blocks they edit and write each change through; a change from another device replaces the copy only while none of this device's writes is still in flight, and otherwise the later write wins, as on the server.
- **Settings live in the synced row.** The weight unit and the rest defaults, which `@AppStorage` held, are the `settings` row with the id `settings`. A device creates the row whole the first time it changes a setting, with the schema defaults in every column it did not touch (`AppSettings.encode` writes a rest default for an unset category, because the columns are `NOT NULL`), and patches it ever after. Two devices that both create it offline would reset each other's other columns to the defaults once, because the server's put replaces the whole row; with one person on one phone that is acceptable. The Levels period stays in `@AppStorage`, because it is view state, not data.
- **The client owns the loop.** `SyncClient` watches `_outbox` and syncs 100 ms after a local write, on launch, on foreground, when the network comes back, on a `head` message from the `/api/live` WebSocket, and every minute. One `POST /api/sync` carries the coalesced outbox with the bundled owner token as a bearer and brings back the rows changed since the cursor. Failures retry with backoff capped at a minute, except a 401, which stops the client until the next launch. There is no sync screen: with the server URL and token fixed per build, the owner has nothing to configure, and the client's status and rejections stay internal.
- **The server and token are build settings.** `AppEnvironment.apiURL` and `AppEnvironment.ownerToken` read `API_URL` and `OWNER_TOKEN` from `Info.plist` and stop the app at launch when either is missing. Debug uses `API_URL` from the generated `LocalSecrets.xcconfig`, which carries the worktree's ports, and the development token pinned in `Config/Base.xcconfig`, so a simulator syncs with the checkout's `bun run start:server` with no setup. Release takes both from env-manager `prod` (`https://a-better-me.stf.lol` and the Worker's `OWNER_TOKEN`) through `bun run env:ios`, which writes the git-ignored `Config/Env.xcconfig`. The token ships inside the Release app; the owner's own phone is the only install, so that is as safe as the device. Rotating the token means `bun run secrets:push` and a new Release build.
