# Hosting

- **One Cloudflare Worker, `a-better-me`.** `wrangler.jsonc` serves `server/src/worker.ts` at the custom domain `https://a-better-me.stf.lol` on the `stf.lol` zone, with `workers.dev` and preview URLs off. It shares the Cloudflare account with procrastimate. The Worker runs the same `handle` from `server/src/api.ts` as the Bun server, so local runs and production share every route. There is no web build in it yet.
- **The space is a Durable Object with SQLite storage.** The `SPACE` binding names the class `Space`, created by the `v1` migration as a `new_sqlite_classes` entry, and the Worker always addresses the one object named `owner`. The object is created on first use, so nothing is provisioned by hand. Its storage keeps 30 days of point-in-time recovery, so a bad write can be rolled back without a backup. The Worker is not placed in a region: there is no database to sit beside, and a request hops to the object wherever it was first created.
- **Settings.** `APP_ENV=production` is a plain var in `wrangler.jsonc`. `OWNER_TOKEN` and `SENTRY_DSN` are Worker secrets, copied from env-manager `prod` by `bun run secrets:push`. The Worker parses them once per isolate, and when a secret is absent it answers every request with a 500 and logs the missing setting.
- **Daily backup to R2.** The cron `0 9 * * *` asks the object for every synced table through the stub's internal `/dump` route, which no public route reaches, and writes `{ at, tables: { <table>: rows[] } }` to `sqlite/<date>.json` in the R2 bucket `a-better-me-backups`, then deletes all but the newest 30. A Sentry cron monitor watches it ([Observability](observability.md)). It prunes by count, not age, so a run of failed days never deletes the last good dumps. The dumps are the readable copy outside Cloudflare's storage; point-in-time recovery is the fast path for the last 30 days.
- **CI deploys `master`.** Every PR runs `wrangler deploy --dry-run` inside `bun run build`. A push to `master` deploys after the Bun and Swift jobs pass: `bun scripts/secrets.ts verify` first fails the job when the Worker lacks a required secret, then `wrangler deploy`. A newer push never cancels a running deploy. The deploy uses the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` repository secrets, which `bun run secrets:github` copies from env-manager `prod`.
- **`scripts/secrets.ts` is the one bridge from env-manager to the cloud.** `push`, `github`, `check` (drift between env-manager, the Worker, and GitHub), and `verify` (CI). It reads values with `env-manager print`, which needs this Mac's AWS access, logs only key names, and hands values to child processes on stdin.
