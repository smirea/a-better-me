# Hosting

- **One Cloudflare Worker, `a-better-me`.** `wrangler.jsonc` serves `server/src/worker.ts` at the custom domain `https://a-better-me.stf.lol` on the `stf.lol` zone, with `workers.dev` and preview URLs off. It shares the Cloudflare account with procrastimate. The Worker runs the same `handle` from `server/src/api.ts` as the Bun server, so local runs and production share every route. There is no web build in it yet.
- **Placed in `aws:us-east-1`.** An upload is a run of sequential queries, each crossing the distance between the Worker and Supabase, so the Worker is pinned beside the database instead of waiting for smart placement to learn the traffic.
- **Postgres through Hyperdrive.** The `HYPERDRIVE` binding is config `a-better-me-prod` (`7d04f2790d4d4dc799760630c557cc32`, caching off), which reaches database `a_better_me` as `a_better_me_app`. Each request opens a postgres.js client over it and ends it after the response; Hyperdrive pools the real connections.
- **Settings.** `APP_ENV=production` and `POWERSYNC_URL` (empty while sync is off) are plain vars in `wrangler.jsonc`. `OWNER_TOKEN` and `POWERSYNC_JWT_PRIVATE_KEY` are Worker secrets, copied from env-manager `prod` by `bun run secrets:push`. The Worker parses them once per isolate, and when one is absent it answers every request with a 500 and logs the missing setting.
- **Daily backup to R2.** The cron `0 9 * * *` dumps every synced table, from one repeatable-read snapshot, as JSON to `postgres/<date>.json` in the R2 bucket `a-better-me-backups`, then deletes all but the newest 30. It prunes by count, not age, so a run of failed days never deletes the last good dumps. Supabase's own backups cover only its `postgres` database, never `a_better_me`.
- **CI deploys `master`.** Every PR runs `wrangler deploy --dry-run` inside `bun run build`. A push to `master` deploys after the Bun and Swift jobs pass: `bun scripts/secrets.ts verify` first fails the job when the Worker lacks a required secret, then `wrangler deploy`. A newer push never cancels a running deploy. The deploy uses the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` repository secrets, which `bun run secrets:github` copies from env-manager `prod`.
- **`scripts/secrets.ts` is the one bridge from env-manager to the cloud.** `push`, `github`, `check` (drift between env-manager, the Worker, and GitHub), `verify` (CI), and `public-key` (the committed PowerSync public key). It reads values with `env-manager print`, which needs this Mac's AWS access, logs only key names, and hands values to child processes on stdin.
