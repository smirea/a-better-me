# Design language

The app merged two reference apps and grew a Dashboard, Pings, and Supplements, so screens drifted into different ways of drawing the same thing. Start from the high-level principles below on every UI task, then apply this app's specific patterns. Components and tokens live in [iOS](ios.md) under "Our own design language"; `app-ios/scripts/lint-swift.ts` fails on the bypasses a line can show.

## Principles

- **Look at similar interactions first.** Before building or editing a screen, row, header, or control, inspect sibling screens and `DesignSystem/` for the existing interaction and reuse it instead of inventing a one-off. When changing a shared concept (date headers, top-4 targets, nutrition rows, formatters, form drafts), audit every sibling screen that shows it so the whole app stays consistent.
- **Zero extra copy.** Write the bare minimum words needed to understand and act. Never add explanatory `Section` footers, helper captions ("Enter how many…", "Picked from the name…", "Pings list in this order…"), redundant titles or headers ("Today" under a selected today pill, "More", repeating a screen title in a section), `"was X"` annotations, implied separators (`"x"` between weight and reps), or redundant close/done buttons when a gesture or `×` already dismisses. A setting row is its title and icon, with its current value where it has one; `SettingToggle` and `SettingLink` take no caption by default. `ThemedSection` has no footer, and `app-ios/scripts/lint-swift.ts` fails on a `Section` footer: state worth showing (a macro sum, a warning) is a row or the section's `subtitle:`. Confirmation alerts say only the consequence ("Logged entries keep their copy."), never "Are you sure" or "This action cannot be undone".
- **Flat content and tight density.** Draw primary content rows, editors, headers, and timelines flat on `Theme.background`—never wrap them in `Theme.surface` card containers or heavy borders just because SwiftUI's `Form`/`List` defaults to boxed sections. Reserve `Theme.surface` cards for Dashboard summary tiles and grouped Settings rows. Reclaim vertical and horizontal space: put titles and metadata inline with controls where possible, keep padding tight, and let charts and lists use the screen.
- **Direct manipulation over chrome.** Tapping an item or its icon edits it directly—never add a separate pencil or Edit icon to a row. Use full-swipe destructive delete on deletable rows, long-press to enter selection mode without conflicting context menus, and drag-down dismissal on drawers. Drop intermediate pickers or dropdowns when the current tab or context already chooses one action.
- **Tabular precision and width budgets.** Primary numbers and macro targets take precedence, right-align, and line up in shared columns across rows regardless of nesting or indentation. Cap secondary metadata (such as serving text at ≤ 30% width, ellipsized, or wrap it underneath on long names) so it never squishes primary values. Use monospace/tabular figures for times and aligned numbers, equal widths for sibling pills or action buttons in a row, and multiline wrapping for titles instead of truncating them.
- **Persist UI and draft state.** Collapsed sections, active tabs and summary panels, the shared shown day, and unsaved sheet/form drafts survive app reloads and phone locks. Never leave user-toggled UI state or in-progress editor input in ephemeral `@State` that resets when the screen restores.
- **Color carries data, icons replace clutter.** Keep chrome neutral (white tint on dark) and reserve color for semantic meaning (macros, goals, muscles, ping swatches, alterations, destructive actions). Prefer compact icons and short 1–2 word labels over truncated text walls, and prefer native SwiftUI / Liquid Glass transitions over custom animations that pop in or hitch.

## App-specific patterns

- **Page and surfaces.** Every screen draws on `Theme.background`. Dashboard overview cards, Strategy's cards, and grouped Settings sections sit in `Theme.surface` with `Theme.cornerRadius` and `Theme.margin` sides (`card()`, `ThemedSection` under `.themedList()`). Content lists, timelines, editors, and detail headers sit flat on `Theme.background`: a `ScrollView` uses `FlatSection`, and a `List` or `Form` calls `.flatList()` (`.flatPlainList()` for a plain list), under which every `ThemedSection`, `NutrientList`, `IngredientsSection`, and in-list `TruncatedList` draws full width on the background with hairline row separators and the app's 20-point margin. Only grouped Settings screens keep `.themedList()` cards.
- **One title.** A tab root has the large leading title beside its toolbar (`screenTitle`), except day-driven tabs (Food Log, Workout, Pings) which replace the bar with the shared `DayHeaderRow`. Pushed screens and sheets have one inline title (`detailTitle`, with a subtitle only for meaningful state such as a program day's gym or Exercises scope). No section header repeats the title or the only row under it.
- **Toolbars.** A tab root's buttons form one glass cluster, ending in a ⋯ menu named for what it acts on (Day Options, Workout Tab Options), never "More", and never a label another screen's menu uses, such as the live workout's Workout Options. Pushed detail screens (`RecipeDetailView` with its heart and Recipe Options, `SupplementDetailView` with Edit and Supplement Options, `WorkoutSummaryView` with Session Options) follow the same rule: keep the trailing cluster to at most two items (for example Favorite + ⋯ or Edit + ⋯) so inline titles stay untruncated on iPhone, putting extra modes and object actions (Prepare, Edit, Duplicate, Start/Stop, Delete) in the ⋯ menu rather than a third toolbar icon or an in-body circle button row. Sheets close with `Button(role: .close)` and confirm with `Button(_, role: .confirm)`; a pushed editor confirms with the same checkmark.
- **One row of controls.** Between the navigation bar and the content sits at most one row: a segmented picker whose labels fit untruncated, an underline tab strip, or one scrolling row of filter chips. A second mode goes into the navigation bar (the Library's Recipes, Foods, Favorites picker in the title's place; Nutrition Overview's Contributors toggle) or a menu (Exercises' Show). Search fields count as part of the bar.
- **Sections.** A flat section is `FlatSection` (hairline top divider + `SectionHeader` with optional muted `subtitle:` and optional underlined trailing action such as See All, Collapse, or Expand All; adding to a section is that text action, `ThemedSection`'s `actions:` "Add", not a round + or a "+ Add" row). `TruncatedList` also draws flat on `Theme.background` with a top hairline divider by default (passing `inList: true` only inside grouped `Form`/`List` screens). Nutrition lists reuse `FlatIngredientsSection`, `FlatNutrientList`, and `FlatNutrientBreakdown` in flat `ScrollView` screens rather than wrapping content in `ThemedSection`.
- **Actions.** Reserve `pinnedActions` (at most one white `primaryPill` at the bottom, with optional glass `secondaryPill`s above it) for flows with a clear commit or advance step (wizards, loggers, creation forms)—never pin a floating white pill over a read-heavy detail page where it obscures scrolled content. Start Workout over a workout's or program day's exercises is the lone floating glass capsule (`floatingAction`), because the owner wanted it big and over the list. Buttons are never filled with a color; color carries data (macros, goals, muscles), and red text marks destructive menu items. A saved favorite's heart is the one colored glyph on an action: `heart.fill` in `Theme.favorite`, on the logger's round heart, the entry editor's Favorite, and a detail screen's toolbar heart, and a second tap removes it. Decorative hearts (the Favorites tab, Apple Health, heart rate) keep their colors. A chip with an icon sets it 6 points from its title (`chipButton`'s label style), as `Chip` does: the system's title-and-icon gap read as too wide inside a small capsule. Reserve `ActionLabel` strictly for in-sheet inline action cards (such as `EntryEditor`) that have no navigation toolbar room—do not add `ActionLabel` rows to pushed detail screens. A row that edits its value opens on a tap of the row (with a chevron), never through a separate Edit chip; a live workout's exercise keeps at most Info, Warm Up, Targets, and Note as chips, and the rest sits in its Exercise Options ⋯. A row's own inline action is a `RowActionButton`.
- **Selection.** Choice rows end in `SelectionMark`, one radio glyph; multi-select rows in its checkbox. Settings choices trail their row as a menu with the current value and an up-down chevron (`SettingChoice`).
- **Stats and numbers.** A number reads over its caption (`StatView`), on the Dashboard, Strategy, insight grids (`InsightTiles`), and detail summaries alike; pass `action:` to `StatView` when a stat is directly editable (shows a subtle `⇕` chevron beside its caption). Use the shared formatters (`Double.niceText`, `wholeText`, `NumberText.plain`, `WeightUnit.label(kg:)`)—no decimals in condensed views, `"cal"` (never `"kcal"`) everywhere in UI copy, and configured Top-4 nutrient targets everywhere targets appear.
- **Charts.** A chart shows a value only when it is tapped, and a drag always moves something: the chart through time on a metric detail screen, the screen, or a pager. See [iOS](ios.md), Charts are interactive.
- **Bottom bars.** One bar at a time. A mode that brings its own action bar (the Food Log's select and paste) hides the tab bar while it lasts. The Pings tab's + turns the tab bar itself into the pings' drawer, which a drag down turns back ([Pings](pings.md)). A lone floating button over a list (Start Workout) gets no band or fade behind it: the content runs under it, and the list's bottom inset is only the button's height, so the last row scrolls clear.
- **Empty states.** `ContentUnavailableView`: icon, title, one line. A section with nothing in it and a way to add elsewhere is hidden rather than drawn empty (the Workout tab's Active Program, Workout Library, and a custom section).
- **Drafts.** Food, recipe, and supplement forms persist their draft with `.persistDraft`, and save, Close, and Delete clear it ([iOS](ios.md), Form drafts outlive the sheet).
- **Verification.** Reusing existing `DesignSystem/` components and patterns should just work once the build passes—do not boot a simulator for small tweaks built on prebuilt components. Boot the simulator (and run `app-ios/scripts/screen-tour --compare` when visual diffing helps) for custom implementations, new gesture/scroll mechanics, or large layout changes; add any brand-new screen to `screen-tour.screens.ts`.
