# iOS

- **The newest iOS, iPhone only.** The minimum target is the newest iOS the installed Xcode ships (iOS 27 with Xcode 27), on iPhone (`TARGETED_DEVICE_FAMILY = 1`), portrait, dark mode, with a companion Apple Watch app on the newest watchOS ([Live workout surfaces](live-workout.md)). There is no legacy support: use the newest APIs and never write `#available` fallbacks. Raise the target when a new iOS ships. The scaffold's macOS, iPad, and Swift package support is dropped, so a simulator build through `xcodebuild` or `./scripts/run` is the only check. CI builds on the `xcode-27` runner image (macOS 27 with Xcode 27, in preview), because `macos-26` only ships Xcode 26.
- **Every permission up front.** It is the owner's own app, so the first launch asks for everything at once instead of when a feature first needs it: one Health sheet for every type the app reads or writes (the Dashboard's, workout recording's, and the dietary types; `AppPermissions` in `Sources/App/Permissions/`), then notifications, camera, and microphone, one after another; Ramble transcribes on the server, so speech recognition is not asked for. Features still check their own access and degrade when it is denied. Live Activities have no request API, so iOS asks when the first one starts. The watch keeps asking only when a workout starts there ([Live workout surfaces](live-workout.md)). Debug simulator builds skip Health unless launched with `-health on` ([Workflow](workflow.md)).
- **Native first, with Liquid Glass.** Prefer a native SwiftUI component whenever one exists (`TabView` with `Tab` roles and `tabViewBottomAccessory`, `NavigationStack` titles and toolbars, `List`, `Form`, `Menu`, sheets, `ContentUnavailableView`, glass effects) and style it with design-system tokens. Build a custom component only when no native one does the job, such as the set-logging row. The tab bar is the native Liquid Glass bar: Dashboard, Nutrition, Workout, More, and a `.prominent` "+" tab that acts instead of selecting. Its `onChange` restores the previous tab and opens that tab's add sheet ([Nutrition](nutrition.md#navigation-shell)). On More the same tab is a back button (a chevron labeled Back): it selects the tab More was opened from, which `RootView` records as `beforeMore`, and Dashboard when nothing opened More yet. The app always launches on Dashboard, so a cold launch that taps More then Back lands there. One `HealthData` lives on `RootView`, which owns the Health access request and refreshes it when the app becomes active; Dashboard and Strategy read it from the environment. More pushes every screen as a value (`MoreRoute`) and registers the destinations of the screens it pushes (Levels' muscles, Strategy's routes) at its root: a value link inside a screen pushed with a view destination never fired. The in-progress workout bar is the tab view's bottom accessory on every tab.
- **Local first on GRDB with the sync engine.** All owner data lives in one SQLite file on the device that GRDB reads and writes. The sync engine's triggers queue every write in `_outbox`, and its client syncs with the server from launch, with the URL and owner token the build bundles. Models are plain structs that are also GRDB records, so they serialize to JSON as they are. Screens observe them with `@Observe` and write through `LocalStore`. SwiftData is gone: its mapping layer and migrations bought nothing for value trees. The design, the column shapes, and the client are in [Sync](sync.md). The phone holds the only copy of the owner's data, so a schema change is additive (a new column that is nullable or has a default) and the client's `migrate()` adds it on launch; the local file is never wiped. The first launch on the engine keeps the PowerSync `ps_data__` tables and writes `a-better-me.before-sync-engine.sqlite` beside the database, so a row the server refuses still exists on the phone; both go in a later release once the owner confirms the server holds everything ([Sync](sync.md#ios)).
- **Our own design language.** The app started as a copy of MacroFactor and MacroFactor Workouts. It now has one consistent look of its own across both halves, so a concept that appears on two screens is one component, drawn the same way. The dark theme and fonts stay, and the accent is blue `#0649DC` (it replaced the reference app's coral `#F28969`), so text and icons on an accent fill are white. The accent means brand, selection, and activity only; a color that carries meaning gets its own token, so a new accent can't change it. `Theme.coral` keeps the old coral for expenditure, steps short of the goal, and caution banners: DM Sans for text, and MacroSans (wide, heavy) only for the watch's and the Live Activity's all-caps labels. iOS ignores variation axes on these variable fonts, so `app-ios/scripts/make-fonts.py` cuts static instances into `Sources/Shared/Resources/Fonts/`. Tokens live in `Sources/Shared/DesignSystem/` (shared with the watch app and the widget extension), including the one macro palette, and iPhone-only components in `Sources/App/DesignSystem/`. Feature code uses them instead of literal colors, font sizes, and copies:
  - `WeekStrip` and `DayPill` for every week of days (Food Log, Workout tab, and the workout month calendar). Days are `CalendarDay`, Monday first; a pill's outline fills with a `DayRing`.
  - `SectionHeader` with `SeeAllLink` for a screen section's title and its text actions, and `SectionTitle` for a list section.
  - `TruncatedList` for any list that grows with use inside a screen with other content: five and a half rows with the half row faded, and See All pushing every row onto its own screen. Screens are judged against a year of data, not a week, and a screen of other content never ends in an unbounded list.
  - `ThemedSection` for every list section (a row background on a `List` doesn't reach its rows, on a `Section` it does), `Chip`, `RoundIconButton`, `UnderlineTabs`, `WizardOption` and `SelectionMark` (every radio and checkbox), `WizardPage` and `WizardProgress` (every wizard step), `StatView` (a number over its caption), `.progressViewStyle(.bar(color))`, `.nameAlert`, and `Binding.isPresent`. Type roles (`AppFont.sectionTitle`, `listTitle`, `rowTitle`, `rowDetail`, `chip`, `badge`), `Theme.margin`, and `Theme.tinyCornerRadius` replace literal sizes.
  - Per area: `ExerciseTile`, `SetBadge`, and `MuscleTileCard` (Workouts); `FoodRow`, `FoodIcon`, `AddToPlateButton`, `MacroHeader`, `MacroTotalsBars`, `ImpactGauges`, and `NutritionFormat` (Nutrition); `ChartLegend` (shown only for two or more series), `ProgressRing`, `CardPicker`, and `.themedYAxis()` (Dashboard). `Int.minuteSecond`, `TimeInterval.countdown`, `WeightUnit.label(kg:)`, and `Double.niceText` and `wholeText` (one decimal under 10, whole above; never a decimal), and `NumberText.plain` (an editable number: set fields, plates, food quantities) are the shared formatters, and `HealthStore.shared` is the app's one `HKHealthStore`.
  - `RowLabel` for icon, title, and detail rows; `primaryPill()` and `secondaryPill()` for full-width actions, placed at a screen's bottom by `pinnedActions { }` (which owns their margins) with `PinnedActionButton` as the primary, `prominentButton(tint:)` for any other prominent button, and `chipButton()` for the small capsule beside a row's value or in a card, and for the actions in a bottom bar or banner (the Food Log's selection and paste bars, the logger banner's time and plate). Their round buttons are `RoundIconButton`; `RowActionButton` is the small circle at a row's end that acts without opening it (add to plate, add or swap an exercise), and `ActionLabel` a detail page's icon-over-title action; `card()` for the surface card; `detailTitle(_:subtitle:)` for inline titles; sheets close with `Button(role: .close)` and confirm with `Button(_, role: .confirm)`; `ShortcutsPanel` for both "+" sheets.
  - The app's tint is white (`Theme.textPrimary`), so toolbar buttons, list icons, pickers, alerts, and prominent buttons are white. Only the tab bar's selection and switches keep the accent; each `Toggle` sets `.tint(Theme.accent)` itself, because SwiftUI doesn't carry a toggle style into sheets and covers. Text on a white fill is `Theme.onPrimary`. The native `.glassProminent` fills with that white tint and keeps white text, so a raw `.buttonStyle(.glassProminent)` renders a blank pill; `app-ios/scripts/lint-swift.ts` fails on one outside `Buttons.swift` (CI's Swift checks and pre-commit run it). Prefer a native button style (`.glass`, `RoundIconButton`) over a label drawn with `.glassEffect` or a hand-filled shape under `.plain`. Screens use 20 pt side margins, and lists and forms call `themedList()` to draw on `Theme.background` instead of the system's black grouped background.
- **Tab titles sit beside their controls.** `screenTitle(_:)` gives every tab root the native `.inlineLarge` title: DM Sans Bold, title case, leading, on the same row as the toolbar's glass buttons, and truncated by the bar when long. The reference app's wide all-caps MacroSans title took its own row under the buttons, so the phone no longer uses it for titles. A toolbar item that comes and goes with the screen's state (the Food Log's Today) stays declared and toggles `.hidden(_:)` from state set in `withAnimation`, so the glass cluster stretches to take it in. An `if` around the item, or an unanimated change such as a day swipe, makes it pop in. Switching tabs is a cut, not a morph: each tab owns its `NavigationStack` and so its own bar, and `TabView` has no transition between them.
- **Code layout.** `Sources/App/` holds the iPhone app, `Sources/Watch/` the watch app, `Sources/Widgets/` the widget extension, and `Sources/Shared/` what all three compile. Each product area gets a folder (`Workouts/`, `Nutrition/`, `Dashboard/`) with one subfolder per feature; what several areas share sits in its own folder (`Body/` for weigh-ins and body metrics, `Health/` for Apple Health reads, `Settings/` for the synced settings row), so no area reaches into another for it. The Xcode project uses a synchronized folder, so new files and resources join the target without editing `project.pbxproj`.
- **Bundled data.** Small read-only data ships in the app bundle under `Sources/App/Resources/`: the catalog's JSON, the body figure, and the gym defaults. Scripts generate it; nobody edits it by hand.
- **One vector body figure draws Levels and every muscle tile.** `app-ios/scripts/body.svg` holds the reference app's male front and back avatars side by side, one path per side and region (silhouette, bone, or muscle) and one `<view>` per crop: each side, and each muscle's tile square, the region the reference app's per-muscle tile shows. Codex derived it from `avatar_male_{front,back}.svg`, matching the crops against the reference tiles, and it is checked in as a hand-made source. `scripts/catalog.ts` flattens it into `Catalog/body.json`, and SwiftUI fills its paths (`BodyFigure`, `BodyCrop`): Levels and the summary crop to a side, and `MuscleTile` crops to the muscle's square with that muscle in the accent. The 22 per-muscle SVG tiles in an asset catalog are gone; Xcode rasterized each at every scale, so they were 5.2 MB of a Release `Assets.car`.
- **Bundled Markdown as one pack.** The catalog's instruction and article Markdown (1,490 texts, 6.5 MB, about 1.9 MB compressed in the download) ships in the app as `Resources/Catalog/markdown.pack`, the UTF-8 texts back to back, and `markdown.json`, each `Instructions/<exercise id>` and `Articles/<article id>` key's byte offset and size, both written by `scripts/markdown-pack.ts`. `MarkdownPack` memory-maps the pack on first use and decodes one text per lookup, so instructions work offline on first launch. SQLite was rejected: lookups are by key only, never a query, so a database adds a dependency and per-row overhead for nothing. One file per text in the bundle would cost a file-system lookup each and inflate the bundle with per-file overhead.
- **Downloaded assets.** The catalog's exercise and equipment images (1,785 files, about 16 MB) live in `app-ios/Assets/`, outside the synchronized folders, so they stay out of the app bundle. They rarely change between builds. Release downloads them from the private bucket `a-better-me-assets` ([Hosting](hosting.md)). Debug downloads them from the worktree's dev server, which serves `app-ios/Assets/` at `$(API_URL)/assets` in the bucket's layout, so local work never needs an upload or bucket credentials. Debug never downloads on its own: launch only reads what is already on disk, and the Settings row's tap starts the download, so a rebuild never re-downloads them. The files ship as packs of about 1 MB, the files in path order back to back (17 requests instead of one per file: thousands of few-KB requests were latency-bound). `buildAssets` (`server/src/assets.ts`) builds the packs and the manifest, which lists each pack's sha256, size, and every file's path, offset, and size. The asset version is the first 16 hex characters of the sha256 of the manifest's pack list. `bun run assets version` rewrites the tracked `Config/Assets.xcconfig`, and a Bun test fails when it is stale. Each build bundles `ASSETS_VERSION` and downloads `manifests/<version>.json`. `AssetStore` (`Sources/App/RemoteAssets/`) verifies each pack's size and hash, unpacks it into a hidden staging directory, and renames that to `Application Support/a-better-me/assets/blobs/<directory>/`, so a pack directory is always whole. The directory name hashes the pack's sha256 together with its file paths and ranges, because a renamed file keeps the pack's bytes and a directory named by them alone would keep the old file name. The folder is excluded from backup. It rejects a manifest whose paths contain `..` or whose ranges overrun their pack. It starts at launch and downloads on Wi-Fi only, through a `URLSession` that refuses expensive and constrained networks. It shows no notification, banner, alert, or badge. The Settings screen's assets row shows `Assets: downloading · X of Y MB` with a progress bar while downloading, and `Assets: downloaded · Y MB` with no bar once done. Tapping it re-checks the manifest and downloads now on any network. It deletes packs and manifests of other versions once every pack is present, including the per-file blobs earlier builds stored. It signs bucket requests itself with SigV4 (`S3Signer`), so there is no SDK. Requests to the dev server go unsigned. Until an image arrives, views show their placeholder and re-render when it lands. A Release build without the bucket settings has downloads off.
- **Performance is a top priority.** The owner noticed lag when tapping almost anywhere, and Sentry recorded app hangs of 4 to 6 seconds on their iPhone in October 2026. A review found one structural cause behind most of it: about ten screens each run their own `@Observe(WorkoutSession.finished)`. Each one decodes the whole history synchronously on main when it appears (GRDB's `.immediate` scheduling), and it decodes it again after every session write, which the sync echo doubles. Dashboard cards, Levels, and the live-workout editor recompute their metrics in `body` over every session on each render. Exercise images are read and decoded at full size on main. The rules that follow from this are in `app-ios/AGENTS.md` under Performance. History is fetched and decoded once by an app-level observer and derived values are memoized, `body` does no data work, nothing reads disk or the database on main, and speed is judged on a Release build on a device.
- **Swipe actions outside a `List` use `rowSwipeActions`.** `List` rows keep SwiftUI's `swipeActions`. Rows in a `ScrollView` use `DesignSystem/RowSwipe.swift`, such as the Food Log's tiles under the day pager, set rows, and weigh-ins. A SwiftUI `DragGesture` there would also capture vertical scrolls, so it is a UIKit pan through `UIGestureRecognizerRepresentable`. The pan begins only on a horizontal drag toward an edge that has actions, and enclosing scroll views wait for it to fail. A vertical drag therefore scrolls, and a drag toward an edge with no actions pages or scrolls the parent.
- **Pagers inside a screen are paging scroll views.** A horizontal pager within a scrolling screen, such as the Dashboard's focus cards, the Food Log's days, and the week strip, is a `ScrollView(.horizontal)` with `.scrollTargetBehavior(.paging)` and `.scrollPosition(id:)`, and `PageControl` (UIKit's `UIPageControl`) draws its dots. A page-style `TabView` hosts each page in a recycled collection view cell and rebuilt the incoming page on every swipe, which made the Dashboard's swipe hitch (Dashboard feedback, Nov 2026). A pager of a few pages keeps them in an eager `HStack`, so they are built once; a long or unbounded one, such as the Food Log's days, stays lazy. Small fixed pagers that are not inside a vertical scroll, such as the Food Log's totals, may stay a `TabView`.
- **Charts are interactive.** Every time-series chart big enough to touch calls `chartScrubbing` (`DesignSystem/ChartScrub.swift`), as Apple Health's charts behave. A tap selects the nearest point and shows a rule and a callout with its date and values. Tapping that point again clears it. A horizontal drag scrubs, and the selection stays after the finger lifts. Each change plays a selection haptic. The gestures are UIKit recognizers, like `rowSwipeActions`, so a vertical drag still scrolls the screen. Inside a horizontal pager, such as the Dashboard's focus cards, a swipe still pages, and a press and hold starts the scrub: the pan looks for a horizontally scrolling view above the view under the touch, because SwiftUI attaches the recognizer above a SwiftUI `ScrollView`. The rule and callout draw in the chart's overlay with their own state, so scrubbing never re-evaluates the marks or re-derives the screen's data. Callers pass precomputed x positions (a bar's middle) and format only the selected point. The callout sits above the plot, except in a pager, where the page would clip it, so it goes beside the rule (`placement: .beside`). Sparklines inside a card or row that is itself a link stay static, because a tap there opens the detail. So do charts that already print every value, such as `WeekTargetsChart`.
- **Confirmations are alerts, never `confirmationDialog`.** Since iOS 26 a confirmation dialog presents as a popover from its source, and a popover drops the dialog's cancel button, so the owner had no way to back out of "Exit the Plate?" but tapping outside. An `.alert` always shows its `Button(role: .cancel)`. `app-ios/scripts/lint-swift.ts` fails on any `.confirmationDialog(` under `Sources/App`; the watch app keeps them, where they present full screen with their cancel.
- **The owner's own packages track `master`, never a commit.** Feedback (`smirea/feedback-engine`) and `smirea/sync-engine` are referenced by branch, and `Package.resolved` is not tracked, so a fresh checkout, CI, and TestFlight resolve each one's latest commit. Xcode keeps a branch package at the revision its local pin names, so `scripts/run` and `scripts/archive` first run `scripts/own-packages.ts`, which moves each pin under `github.com/smirea/` to its branch's current head. Dropping the pin is not enough, since Xcode then re-resolves the branch from its stale cached mirror. When GitHub can't be reached, the pins stay, the script says why, and the build uses what it has. CI saves its package cache under a key per run, so what it has is the previous run's packages; a fixed key once froze a months-old feedback-engine whose product was still named Feetback. Third-party packages keep their declared requirements: Sentry is an exact version, and GRDB comes through sync-engine's range. Building from the Xcode app does not refresh; use the run script, or File › Packages › Update to Latest Package Versions.
- **Shake-to-feedback in every build.** Feedback (`https://github.com/smirea/feedback-engine`, branch `master`) turns a shake into a frozen screenshot the owner annotates by tapping components, and exports one file, an annotated image or a JSON report, that names each component's `file:line` (and, in JSON, its data), so an agent can act on the feedback without guessing. `Observe` conforms to Feedback's `FeedbackRepresentable`, so a screen reports the values it observes instead of skipping them. `App.init` calls `Feedback.enable()` in Debug and Release alike, so the owner's phone and TestFlight builds open the editor on shake, as the package's example app does. It was Debug-only at first, but the phone runs Release, so shaking it did nothing. Its capture flips a private accessibility switch looked up with `dlsym`; drop the package from Release if App Store processing ever flags it. Its Share menu also posts to ProcrastiMate: a task with the annotated image and the JSON report as notes, in a project picked there. It signs in with the session ProcrastiMate keeps in the team's shared keychain group, as Notouroboros does, so `Config/App.entitlements` lists `keychain-access-groups` with the app's own `$(AppIdentifierPrefix)com.stefan.a-better-me` first and `$(AppIdentifierPrefix)com.stefan.shared` second. Keychain writes without a group go to the first entry, so anything a-better-me stores later stays private to it. Without ProcrastiMate signed in on the device, the picker says so. **Add** saves the post to the package's outbox and closes at once, so a post made on a poor connection or none goes out later (at launch, on foreground, or when the network returns) instead of timing out. A post on a weak connection once spun and stopped with its error hidden under the project list. A failure shows at the top of the sheet with its details and **Copy Error**. The tab roots, the screens they push most, the sheets with their own editors, and the repeated rows and cards (dashboard cards, food log hours and entries, `FoodRow`, history rows, library rows, set rows) end their `body` with `.feedback(self)`. Set rows are a builder function, so they pass explicit `data:`. App context names the sync endpoint and pending writes, the live workout and history counts, and the asset status. Screens follow Feedback's accessibility skill (`skills/feedback-accessibility` in the package repo): accessibility is made right for VoiceOver first, and tags are added on top only where a tap would otherwise be ambiguous, so a single tap on any card, chart, section, or row selects that region and never falls through to the whole screen. Every screen and sheet ends its `body` with `.feedback(self)`, and so do rows, cards, and sections that are their own structs. Regions a screen draws in helper functions (a summary, a chart, a section) are tagged where they are drawn, named with the noun a person would say and given the values they already show as `data:`, never a store or a value computed only for the tag. Charts are always tagged, since their axes and gaps are not accessibility elements. Shared containers tag themselves: `TruncatedList` takes its title as its name and reports its caller's `file:line`, `ChartLegend` and `BodyMap` end with `.feedback(self)`, and `ThemedSection` tags each row's `listRowBackground`, the one view that fills a `List` or `Form` cell, so a tap on a row's padding selects the row; SwiftUI exposes no frame for a whole list section. A card that reads as one VoiceOver sentence keeps `.combine` and tags the values inside it that someone would comment on, such as the Steps header's count and goal bar. A section without a title or subtitle renders no header, which used to leave an empty, unlabeled VoiceOver element. Tags are a plain `UIView` behind each view and cost nothing per frame: a Release simulator build scrolled History and the 547-row exercise list with the same CPU time and memory with and without them.
- **Verification.** A change is done when it builds for the simulator and the agent has driven the changed interaction in the simulator and checked the result. Each worktree uses its own simulator, which `agent-simulator udid` creates and claims, named after the worktree directory on the newest iPhone Pro and iOS runtime, so parallel agents never share app state: `app-ios/scripts/run -t "$(agent-simulator udid)" --headless --no-watch`. T3 Code's device tools are the driver: `device_open` streams the simulator to the owner's Device panel and returns one `agent-device` command path bound to that device and session, which injects touches without the Mac's mouse (`snapshot -i`, `press 'label="Save"' --settle`, `fill`, `screenshot`). Debug simulator builds seed realistic volume at launch (`DevSeed`: 30 workouts, an active program, 45 days of food and weigh-ins, and a food library), with fixed row ids so a reinstall against the same server converges instead of duplicating, so every agent sees 20 to 50 rows per list without a flag; `-noSeed` starts empty. Launch arguments go through `xcrun simctl launch`. There is no fallback driver. A Device Hub mouse driver existed while device tools were off, but it moved the real mouse and serialized every agent behind one lock, so it was removed once device tools worked. Device access is a T3 Code setting the owner controls. Pure logic, such as Levels math, progression, and the Dashboard's metrics, lives in plain functions apart from views. The hosted `AppTests` target runs Swift Testing suites from `app-ios/Tests/`, one subfolder per feature, with `@testable import App`; `app-ios/scripts/test <Suite>` runs them locally on the worktree's simulator, and CI's Swift `tests` task runs them on every PR. The wrapper exists because a plain `xcodebuild test` on a simulator with an active Live Activity (an in-progress workout keeps one) raced `liveactivitiesd`: installing the new build ended the activity, the daemon launched the app in the background to deliver that, and xcodebuild's own launch came back with no process. The wrapper installs the test host first and lets that launch pass. Agents answer Health's authorization sheet with `scripts/run --grant-permissions`, never by hand: `agent-device` reads the sheet as one node, and XCTest reports its frames relative to the sheet ([callstack/agent-device#4226](https://github.com/callstack/agent-device/issues/4226)).

## TestFlight

- **TestFlight builds come from GitHub Actions.** `.github/workflows/testflight.yml` runs `app-ios/scripts/archive` on the `xcode-27` runner for every push to `master` that touches `app-ios/`, `scripts/secrets.ts`, or the workflow, and on a manual dispatch; never on pull requests. It copies procrastimate's setup. Pushes share one concurrency group that cancels the run in progress, and a Linux debounce job waits ten minutes first, skipping the archive only when a newer commit on `master` touched the same paths, so a burst of merges uploads once and the macOS runner is claimed only for a build that uploads. The App Store Connect app is `A Better Me` (bundle id `com.stefan.a-better-me`, team `FNYFHG5SV7`); its record had to be made by hand, since the API cannot create apps.
- **Unsigned archive, entitlements ad-hoc signed, export signs.** The archive runs with `CODE_SIGNING_ALLOWED=NO`, because automatic signing at archive time asks for an Apple Development certificate and every fresh runner would mint another "Created via API" one until the account hits its cap. Export keeps only the entitlements a bundle is already signed with, so an unsigned archive shipped without HealthKit or the app group. The script therefore ad-hoc signs each bundle in the archive with `Config/<target>.entitlements`, innermost first (Xcode refuses ad-hoc signing at archive time for targets with capabilities), and fails when a bundle has no such file. `xcodebuild -exportArchive` with `-allowProvisioningUpdates` and the API key then signs every bundle with the cloud-managed Apple Distribution identity and uploads (`--export-only` writes the `.ipa` instead).
- **Settings and keys.** The archive runs `bun run env:ios`, which reads env-manager `prod` locally and the process environment in CI when it holds every Release setting. The App Store Connect team key (Admin role, shared with procrastimate) lives in env-manager `prod` as `ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_PRIVATE_KEY_B64` (the `.p8` base64 on one line) under the `scripts` target. `bun run secrets:github` mirrors it, `SENTRY_AUTH_TOKEN`, the Cloudflare credentials (for the asset upload, a no-op once CI's assets job ran), and the Release settings to repository secrets. The job writes the key to the runner's temp directory, and the script refuses a key inside the repository. The App target's `upload-dsyms` phase sends the dSYMs to Sentry during the archive.
- **Build number is the UTC time** as `year.MMdd.HHmmss` (three integers, the first at most four digits, as `CFBundleVersion` requires), passed as `CURRENT_PROJECT_VERSION` so the watch app and widgets match. `BUILD_NUMBER` overrides it. The marketing version stays `1.0`.
- **Upload requirements in the project.** `Config/Info.plist` sets `ITSAppUsesNonExemptEncryption` to `false` (HTTPS only), so builds skip the export compliance question. `Sources/App/PrivacyInfo.xcprivacy` declares no tracking, crash, performance, and other diagnostic data not linked to the user (Sentry sets no user), and `UserDefaults` with reason `CA92.1`; App Store Connect rejects uploads that use a required-reason API undeclared, so a new one (file timestamps, disk space, system boot time) needs its entry in the same change.
