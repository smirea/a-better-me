# iOS

- **The newest iOS, iPhone only.** The minimum target is the newest iOS the installed Xcode ships (iOS 27 with Xcode 27), on iPhone (`TARGETED_DEVICE_FAMILY = 1`), portrait, dark mode, with a companion Apple Watch app on the newest watchOS ([Live workout surfaces](live-workout.md)). There is no legacy support: use the newest APIs and never write `#available` fallbacks. Raise the target when a new iOS ships. The scaffold's macOS, iPad, and Swift package support is dropped, so a simulator build through `xcodebuild` or `./scripts/run` is the only check. CI builds on the `xcode-27` runner image (macOS 27 with Xcode 27, in preview), because `macos-26` only ships Xcode 26.
- **Native first, with Liquid Glass.** Prefer a native SwiftUI component whenever one exists (`TabView` with `Tab` roles and `tabViewBottomAccessory`, `NavigationStack` titles and toolbars, `List`, `Form`, `Menu`, sheets, `ContentUnavailableView`, glass effects) and style it with design-system tokens. Build a custom component only when the reference app's interaction has no native equivalent, such as the set-logging row. The tab bar is the native Liquid Glass bar: "+" is a `.prominent` tab that opens a sheet instead of selecting, and the in-progress workout bar is the tab view's bottom accessory.
- **Local first on GRDB with the sync engine.** All owner data lives in one SQLite file on the device that GRDB reads and writes. The sync engine's triggers queue every write in `_outbox`, and its client syncs with the server from launch, with the URL and owner token the build bundles. Models are plain structs that are also GRDB records, so they serialize to JSON as they are. Screens observe them with `@Observe` and write through `LocalStore`. SwiftData is gone: its mapping layer and migrations bought nothing for value trees. The design, the column shapes, and the client are in [Sync](sync.md). The phone holds the only copy of the owner's data, so a schema change is additive (a new column that is nullable or has a default) and the client's `migrate()` adds it on launch; the local file is never wiped. The first launch on the engine keeps the PowerSync `ps_data__` tables and writes `a-better-me.before-sync-engine.sqlite` beside the database, so a row the server refuses still exists on the phone; both go in a later release once the owner confirms the server holds everything ([Sync](sync.md#ios)).
- **Look like MacroFactor Workouts.** Dark theme, the reference app's accent colors, and its fonts: DM Sans for text and MacroSans (wide, heavy) for all-caps screen titles, drawn by the native navigation bar. iOS ignores variation axes on these variable fonts, so `app-ios/scripts/make-fonts.py` cuts static instances into `Sources/Shared/Resources/Fonts/`. Tokens live in `Sources/Shared/DesignSystem/` (shared with the watch app and the widget extension) and iPhone-only components in `Sources/App/DesignSystem/`. Feature code uses them instead of literal colors and font sizes. The app's tint is white (`Theme.textPrimary`), so toolbar buttons, list icons, pickers, alerts, and prominent buttons are white like the reference app's chrome. Only the tab bar's selection and switches keep the accent; each `Toggle` sets `.tint(Theme.accent)` itself, because SwiftUI doesn't carry a toggle style into sheets and covers. Screens use 20 pt side margins, and lists and forms call `themedList()` to draw on `Theme.background` instead of the system's black grouped background.
- **Code layout.** `Sources/App/` holds the iPhone app, `Sources/Watch/` the watch app, `Sources/Widgets/` the widget extension, and `Sources/Shared/` what all three compile. Each product area gets a folder (`Workouts/` for now) with one subfolder per feature. The Xcode project uses a synchronized folder, so new files and resources join the target without editing `project.pbxproj`.
- **Bundled data.** Small read-only data ships in the app bundle under `Sources/App/Resources/`: the catalog's JSON, the body figure, and the gym defaults. Scripts generate it; nobody edits it by hand.
- **One vector body figure draws Levels and every muscle tile.** `app-ios/scripts/body.svg` holds the reference app's male front and back avatars side by side, one path per side and region (silhouette, bone, or muscle) and one `<view>` per crop: each side, and each muscle's tile square, the region the reference app's per-muscle tile shows. Codex derived it from `avatar_male_{front,back}.svg`, matching the crops against the reference tiles, and it is checked in as a hand-made source. `scripts/catalog.ts` flattens it into `Catalog/body.json`, and SwiftUI fills its paths (`BodyFigure`, `BodyCrop`): Levels and the summary crop to a side, and `MuscleTile` crops to the muscle's square with that muscle in the accent. The 22 per-muscle SVG tiles in an asset catalog are gone; Xcode rasterized each at every scale, so they were 5.2 MB of a Release `Assets.car`.
- **Downloaded assets.** The catalog's exercise and equipment images and its instruction and article Markdown (about 23 MB) live in `app-ios/Assets/`, outside the synchronized folders, so they stay out of the app bundle. They rarely change between builds. Release downloads them from the private bucket `a-better-me-assets` ([Hosting](hosting.md)). Debug downloads them from the worktree's dev server, which serves `app-ios/Assets/` at `$(API_URL)/assets` in the bucket's layout, so local work never needs an upload or bucket credentials. Debug never downloads on its own: launch only reads what is already on disk, and the More row's tap starts the download, so a rebuild never re-downloads 23 MB. `scripts/catalog.ts` writes them and refreshes the asset version: the first 16 hex characters of the sha256 of the manifest's sorted file list. `bun run assets version` rewrites the tracked `Config/Assets.xcconfig`, and a Bun test fails when it is stale. Each build bundles `ASSETS_VERSION` and downloads `manifests/<version>.json`. `AssetStore` (`Sources/App/RemoteAssets/`) keeps verified blobs in `Application Support/a-better-me/assets/`, excluded from backup. It starts at launch and downloads on Wi-Fi only, through a `URLSession` that refuses expensive and constrained networks. It shows no notification, banner, alert, or badge. The More tab's one row shows `Assets N/total · X MB left`; tapping it re-checks the manifest and downloads now on any network. It deletes blobs and manifests of other versions once every file is present. It signs bucket requests itself with SigV4 (`S3Signer`), so there is no SDK. Requests to the dev server go unsigned. Until a file arrives, views show their placeholder and re-render when it lands. A Release build without the bucket settings has downloads off.
- **Verification.** A change is done when it builds for the simulator and the agent has driven the changed screen in the simulator and looked at a screenshot. Each worktree uses its own simulator, named after its branch (`xcrun simctl create <branch> "iPhone 18 Pro"`), so parallel agents never share app state. T3 Code's device tools are the driver: `device_open` streams the simulator to the owner's Device panel and returns an `agent-device` command that injects touches by accessibility ref (`snapshot -i`, `click @eN`, `fill`, `screenshot`) without the Mac's mouse. Launch arguments such as `-seedSampleData` go through `xcrun simctl launch`. There is no fallback driver. A Device Hub mouse driver existed while device tools were off, but it moved the real mouse and serialized every agent behind one lock, so it was removed once device tools worked. Device access is a T3 Code setting the owner controls. Pure logic, such as Levels math, progression, and the Dashboard's metrics, lives in plain functions apart from views. The hosted `AppTests` target runs Swift Testing suites from `app-ios/Tests/`, one subfolder per feature, with `@testable import App`; `xcodebuild test -scheme App` runs them locally and CI's Swift `tests` task runs them on every PR.
