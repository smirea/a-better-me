# iOS

- **The newest iOS, iPhone only.** The minimum target is the newest iOS the installed Xcode ships (iOS 27 with Xcode 27), on iPhone (`TARGETED_DEVICE_FAMILY = 1`), portrait, dark mode. There is no legacy support: use the newest APIs and never write `#available` fallbacks. Raise the target when a new iOS ships. The scaffold's macOS, iPad, and Swift package support is dropped, so a simulator build through `xcodebuild` or `./scripts/run` is the only check. CI builds on the `xcode-27` runner image (macOS 27 with Xcode 27, in preview), because `macos-26` only ships Xcode 26.
- **Native first, with Liquid Glass.** Prefer a native SwiftUI component whenever one exists (`TabView` with `Tab` roles and `tabViewBottomAccessory`, `NavigationStack` titles and toolbars, `List`, `Form`, `Menu`, sheets, `ContentUnavailableView`, glass effects) and style it with design-system tokens. Build a custom component only when the reference app's interaction has no native equivalent, such as the set-logging row. The tab bar is the native Liquid Glass bar: "+" is a `.prominent` tab that opens a sheet instead of selecting, and the in-progress workout bar is the tab view's bottom accessory.
- **Local first on PowerSync and GRDB.** All owner data lives in one SQLite file on the device that PowerSync manages and GRDB reads and writes, and syncs with the server when a token is stored. Models are plain structs that are also GRDB records, so they serialize to JSON as they are. Screens observe them with `@Observe` and write through `LocalStore`. SwiftData is gone: its mapping layer and migrations bought nothing for value trees. The design, the column shapes, and the connector are in [Sync](sync.md). While no real data exists, a schema change may still wipe the local file instead of migrating; PowerSync re-downloads what the server has.
- **Look like MacroFactor Workouts.** Dark theme, the reference app's accent colors, and its fonts: DM Sans for text and MacroSans (wide, heavy) for all-caps screen titles, drawn by the native navigation bar. iOS ignores variation axes on these variable fonts, so `app-ios/scripts/make-fonts.py` cuts static instances into `Sources/App/Resources/Fonts/`. Tokens live in `Sources/App/DesignSystem/`. Feature code uses them instead of literal colors and font sizes.
- **Code layout.** `Sources/App/` holds the app. Each product area gets a folder (`Workouts/` for now) with one subfolder per feature. The Xcode project uses a synchronized folder, so new files and resources join the target without editing `project.pbxproj`.
- **Bundled data.** Large read-only data, such as the exercise catalog and its images, ships in the app bundle under `Sources/App/Resources/`. It is generated by scripts and never edited by hand.
- **Verification.** A change is done when it builds for the simulator and the agent has driven the changed screen in the simulator and looked at a screenshot. Each worktree uses its own simulator, named after its branch (`xcrun simctl create <branch> "iPhone 18 Pro"`), so parallel agents never share app state. T3 Code's device tools are the driver: `device_open` streams the simulator to the owner's Device panel and returns an `agent-device` command that injects touches by accessibility ref (`snapshot -i`, `click @eN`, `fill`, `screenshot`) without the Mac's mouse. Launch arguments such as `-seedSampleData` go through `xcrun simctl launch`. There is no fallback driver. A Device Hub mouse driver existed while device tools were off, but it moved the real mouse and serialized every agent behind one lock, so it was removed once device tools worked. Device access is a T3 Code setting the owner controls. Pure logic, such as Levels math, progression, and the Dashboard's metrics, lives in plain functions apart from views. The hosted `AppTests` target runs Swift Testing suites from `app-ios/Tests/`, one subfolder per feature, with `@testable import App`; `xcodebuild test -scheme App` runs them locally and CI's Swift `tests` task runs them on every PR.
