# Environment

- **One schema, generated projections.** The root `.env` declares every setting with its type and target. The root `.env.local` holds the current environment's values. `env-manager gen` writes each target's values file and `src/env.ts` reader. Never edit a child values file or reader by hand.
- **Two environments in AWS: `dev` and `prod`.** Project `a-better-me` in env-manager. `dev` is for local development, `prod` for deploys. `env-manager env set <env>` switches and downloads that environment, `env-manager down` re-pulls it, and `env-manager up` pushes edits. `.env.local` records which environment its values came from (`# env-manager values env:`), and `up` refuses to upload values pulled for a different environment, so dev values can't land in prod. Switching to an environment that doesn't exist yet keeps the current values and seeds it on the next `up`. Use the global `env-manager` for both: it loads the AWS credentials from its own checkout, which the pinned copy in `node_modules` cannot see. There is no `local` environment.
- **Agents and CI never need AWS.** Worktree setup and CI run `env-manager gen --local`, which uses the schema defaults. So every default must be harmless and enough to start the app and run the tests.
- **A new setting's values go up after its PR merges.** The agent that added it runs `env-manager env set <env>`, sets the value, and `env-manager up` from its worktree, for each environment that needs one, then `bun scripts/secrets.ts push` for a Worker secret. The `env set` first matters: a worktree's `.env.local` holds schema defaults, and `up` uploads what is there. Uploading before the merge would hand master's deploy a value its code doesn't read yet, and a merge that lands before the upload fails the deploy's `secrets verify` once, which the agent reruns after pushing.
- **Worktrees get their own ports.** `scripts/setup-worktree.ts` writes a git-ignored `.env.override` with the worktree's ports: the main checkout's plus `10000 + (n - 1) * 1000` for worktree n, each keeping its offset. Worktree 1 serves web and API on 16150/16151 and `wrangler dev` on 16152, worktree 2 on 17150/17151/17152. setup-new-app hands out main ports 10 apart, so apps never collide as long as each keeps its ports inside its 10-port slot. Slots stop below 49152, where macOS's ephemeral ports begin. env-manager applies it on top of the root values for every target, and never uploads it.
- **Secrets are optional in the schema and required in `config.ts`.** That keeps offline generation working. `server/src/config.ts` lists the settings production needs in `REQUIRED_IN_PRODUCTION`, and the server refuses to start without them, instead of failing on the first request that reads one.
- **`APP_ENV`** is `development` in `dev` and `production` in `prod`.
- **Release iOS reads `prod`.** `bun run env:ios` uploads the app's assets, then writes Release's `API_URL` (`https://a-better-me.stf.lol`), `OWNER_TOKEN`, `SENTRY_DSN_IOS`, and the asset bucket settings from env-manager `prod` into the git-ignored `app-ios/Config/Env.xcconfig`. It fails when any of them is unset. Debug iOS uses the generated `LocalSecrets.xcconfig`, the development token, and the dev server for assets. See [Sync](sync.md#ios).
- **Asset bucket settings.** The `app-ios` target's `ASSETS_URL` (the bucket's S3 URL, ending in `/a-better-me-assets`), `ASSETS_ACCESS_KEY_ID`, and `ASSETS_SECRET_ACCESS_KEY` are a read-only R2 token's S3 credentials ([Hosting](hosting.md)). Only Release reads them, through `bun run env:ios`, so the `dev` environment needs no bucket values. Debug ignores them, because `Config/Base.xcconfig` points it at the dev server's `$(API_URL)/assets` with no credentials. The app refuses to start when `ASSETS_URL` is set but not http(s), or when exactly one credential is set. An empty `ASSETS_URL` turns downloads off. `ASSETS_VERSION` is not a setting: the tracked `app-ios/Config/Assets.xcconfig` holds it.
- **Server and scripts secrets.** The `server` target holds `OWNER_TOKEN`, empty in `dev`, where every local server uses the development token, `SENTRY_DSN` ([Observability](observability.md)), and `GEMINI_API_KEY` for photo logging ([Nutrition](nutrition.md)). The `scripts` target holds the Cloudflare deploy credentials shared with procrastimate's account. There is no database setting: the Bun server's data is the git-ignored `.data/<checkout directory>.sqlite`, and the Worker's is its Durable Object. See [Sync](sync.md).
