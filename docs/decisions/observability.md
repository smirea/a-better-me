# Observability

- **Two Sentry projects in org `self-uo7`, region `https://us.sentry.io`.** `a-better-me-worker` takes the Worker, its Durable Object, and the Bun dev server. `a-better-me-ios` takes the app. procrastimate's projects live in the same org.
- **The DSNs are env-manager settings, not code.** `SENTRY_DSN` is in the `server` target and `SENTRY_DSN_IOS` in the `app-ios` target, both set in `dev` and `prod`. Schema defaults are empty, so CI, tests, and fresh worktrees report nothing. A DSN is public, so it is no secret, but keeping it in env-manager lets every runtime switch reporting on or off the same way.
- **Production requires the worker DSN.** `SENTRY_DSN` is in `REQUIRED_IN_PRODUCTION`, so `bun run secrets:push` copies it to the Worker as a secret and CI's `secrets.ts verify` refuses to deploy without it. Elsewhere an empty DSN turns Sentry off, and the Bun server logs `Sentry: off`. A DSN of the wrong shape fails `parseConfig` in every environment. The environment is the server's `APP_ENV`.
- **The Worker.** `server/src/worker.ts` wraps its handlers in `withSentry` and the `Space` Durable Object class in `instrumentDurableObjectWithSentry`, both reading the DSN through `parseConfig`. When the config does not parse, Sentry stays off for that request, so `fetch` still answers the 500 that names the missing setting. `cronTriggersIntegration` sends check-ins for the backup cron to the monitor `a-better-me-backup`. A backup that throws, or never runs, alerts. `wrangler.jsonc` sets `nodejs_als`, which the SDK needs for its per-request scope.
- **The Bun dev server.** `server/src/index.ts` calls `@sentry/bun`'s `init` before `Bun.serve` when `SENTRY_DSN` is set, so a local run with env-manager `dev` reports under `development`.
- **Sync reporting lives in `handle`.** `server/src/api.ts` takes a `Report`, which is the `@sentry/bun` or `@sentry/cloudflare` module itself, so both runtimes report the same events and `api.test.ts` checks them with a recorder. The engine answers 200 when it refuses writes and the device drops them, so `handle` reads a `/api/sync` response once and hands it back unchanged.
- **Warning or error.** A write the schema refused is a warning: the server works, and a client sent what it should not. It goes out as one message per response, `Sync rejected writes to <tables>`, with each write's `seq`, table, id, and reason as extras, and it is grouped by its set of tables. A 5xx answer and a thrown error are errors: they are server bugs. The Bun SDK reports a thrown error itself, and the Worker's `fetch` catches one, reports it, and answers 500. Messages carry no stack trace, so the issue title is the message. Both servers drop the SDK's `Dedupe` integration: it discards an event equal to the one before it, which silently lost every refusal after the first in a run.
- **iOS.** sentry-cocoa is pinned exactly in `App.xcodeproj`, linked into App only as its `Sentry-Dynamic` product (the static product embeds an unsigned stub that App Store Connect rejects, as procrastimate found). `Sync/Telemetry.swift` is its only user. `Telemetry.start()` runs first in `BetterMeApp.init` when `AppEnvironment.sentryDSN` is set and the process is not a unit test run. Crash reporting is the SDK default. Debug reports as `development`, Release as `production`. `Telemetry.watch` observes the sync client and sends one warning per distinct `failed` reason, one for `unauthorized`, and one per distinct refused write while the app runs. Being offline is not reported.
